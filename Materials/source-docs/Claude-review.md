## 第一轮：三个研究点的重构

### 问题诊断

原始草案的三个研究点存在三个结构性缺陷：

| 问题 | 具体表现 |
|------|----------|
| **研究点 3 不构成独立贡献** | "PD+CP 端到端协同评估"本质上是把前两个点的成果拼起来跑 benchmark，不能作为硕士论文的第三个创新点 |

### 修改方案

**研究点 1**（KV Cache 传输与布局适配）—— 从工程适配文档升级为系统化问题求解：

- 将 GQA TP 异构、PP/MTP 层划分、融合算子三个子问题统一抽象为"PD 分离场景下的 KV Cache 布局映射与高效转换问题"

**研究点 2**（Decode 动态 CP）—— 明确 RFC 归属和增量贡献：

- 将"陈潇在 RFC 中提出"改为"本课题前期在 RFC 中提出"
- 新增一句总结昇腾平台的增量贡献："将 RFC 中与硬件无关的调度架构在昇腾平台（NPU 图模式、AscendDirectTransport、HCCL 通信域）上完成系统实现，并针对昇腾高计算/访存比下 Decode 访存瓶颈更突出的特点，验证了动态 CP 在昇腾平台上的收益边界与适用条件"

**研究点 3**（运行时 DP 动态扩缩容 + TP 域 KV 去冗余）—— 全新内容：

- 子机制 A：Decode 运行时 DP 动态扩缩容（对应 RFC Road Map Final Release 的 Dynamic Domain Instantiation + Dynamic DP Load Balancing）

**新的逻辑链路**：

> 点2（动态CP）→ 解决 Decode 节点内长/短请求的 KV 访存负载均衡（单节点效率）
> 点3（DP扩缩+KV去冗余）→ 使 Decode 集群具备运行时弹性和存储效率（集群级优化）

## 第二轮：注入"昇腾计算/访存比 + 长上下文"红线

### 问题诊断

原始草案虽然在第 19 行提到了昇腾高计算/访存比，但全文其余部分读起来像通用系统优化——同样的方案搬到 NVIDIA GPU 上也基本成立。需要让评委在每一页都能感受到"这个问题为什么在昇腾上特别严重"和"长上下文如何放大了这个问题"。

### 核心策略

建立一个**量化锚点**（第 19 行），让后续所有论述有具体的数字和公式可以回扣，而不是反复说同一句定性的话。

### 修改点

**1. 第 19 行（选题背景-硬件特征段）—— 全文锚点，完全重写**

修改前：一句定性描述（"昇腾 NPU 往往体现出更高的计算/访存比"），没有数字，没有公式，没有因果链。

修改后：

```latex
昇腾 910 系列的 FP16 峰值算力与 HBM 带宽之比约为同代 NVIDIA GPU 的
1.5--2 倍，这意味着每单位 HBM 带宽需要支撑更多的计算操作，访存更容易
成为系统瓶颈。这一差异在长上下文 Decode 阶段尤为关键。Decode 阶段每
生成一个 token，需要从 HBM 读取模型权重（约 $2\times$ 参数量字节）
和该请求的完整 KV Cache（约 $2 \times n_\text{layers} \times L
\times n_\text{kv\_heads} \times d_\text{head}$ 字节，其中 $L$ 为
当前上下文长度）。当 $L$ 增长至 128K 乃至 1M，KV Cache 读取量远超
权重读取量，成为 HBM 访问的主导成分；此时昇腾高计算/访存比导致计算
单元等待数据的时间占比更高，算力利用率更低。
```

**关键要素**：
- 具体数值：1.5--2 倍
- 显式公式：KV Cache 大小 = f(L)，说明线性增长关系
- 因果链：L 增长 → KV Cache 读取主导 HBM 访问 → 昇腾高计算/访存比 → 算力等待 → 利用率低
- 阶段差异：Prefill 偏计算（高算力是优势）vs Decode 偏访存（高算力是负担）

**2. PD 分离文献综述结尾 —— 三方面 HBM 压力**

修改前：仅提到"D 侧 KV Cache 拉取、重排和 PageAttention 访问没有针对性优化"。

修改后新增：

```latex
128K 上下文的单请求 KV Cache 可达数十 GB，PD 分离需在 P/D 之间传输
同等体量的数据，而 D 侧每个 Decode step 都需从 HBM 遍历等量的 KV
Cache。如果 D 侧 KV Cache 拉取、重排和 PageAttention 访问没有针对
性优化，昇腾有限的 HBM 带宽将同时承受 KV 传输读、layout 转换写和
PageAttention 读三方面压力。
```

**3. CP 文献综述结尾 —— DCP 本质是"降访存"**

修改后新增段落：

```latex
在昇腾平台上，DCP 的收益不仅体现在显存节省，更体现在 Decode 访存压力
的削减。...将 KV Cache 按序列维度分片后，每个设备仅需访问其负责分片
对应的 KV 数据，HBM 读取量随 CP 度近似线性下降。因此，DCP 在昇腾长
上下文 Decode 中的作用不仅是"省显存"，更是"降访存"——用可控的跨
卡通信换取 HBM 带宽压力的缓解，而这恰恰是对昇腾高计算/访存比短板的对
症下药。
```

**4. 研究点 1 动机段 —— KV 传输量与上下文长度的定量关系**

在原有开头后插入：

```latex
这一传输的数据量直接由上下文长度决定——以 Qwen3-235B 为例，128K
上下文的单请求 KV Cache 约数十 GB——而昇腾 P/D 节点间的 HCCL/HCCS
或 RDMA 链路带宽有限，KV 传输时间在端到端延迟中的占比随上下文长度
线性增长。
```

**5. 研究点 2 动机段 —— "访存 straggler"效应**

完全重写动机段落，新增昇腾特异的 straggler 分析：

```latex
这一分布特性在昇腾平台上会触发一种特定的"访存 straggler"效应：一个
超长请求的 KV Cache working set 可达数 GB，若集中落在某个 DP 副本
上，该副本每个 Decode step 都需从 HBM 遍历完整 KV Cache——在昇腾
高计算/访存比下，访存时间主导 ITL，而同一 Domain 内其他 DP 副本的
计算单元因无数据可算而空转。此时，空转副本的算力不仅未能提升吞吐，
反而因为 straggler 副本的尾部延迟拖慢了整个 batch。
```

**6. 研究点 3 第二挑战 —— TP KV 冗余的长上下文代价量化**

修改前：一句话带过"TP 开启后 KV Cache 在各 rank 间形成全量副本，显著放大显存占用"。

修改后：用量化例子展开成完整论证——

```latex
以 128K 上下文的 Qwen3-235B 为例，单副本 KV Cache 可达数十 GB；
若开启 TP=4，每卡需额外存放 3 份冗余 KV Cache，在昇腾有限的 HBM
容量中挤占了原本可用于扩大 batch size 或支撑更长上下文的宝贵空间。
...形成了"不开 TP 算力不足、开 TP 显存放不下"的两难困境。这一矛盾
的根因在于：TP 通过复制权重和 KV Cache 来换取计算并行度，但 KV
Cache 的大小随上下文长度线性增长，长上下文下复制的代价超过并行收益。
```

**7. 评价指标体系 —— 加入昇腾特异的评估维度**

在评价指标段末尾新增：

```latex
通过 HBM 读写量随上下文长度的变化曲线和 AI Core 利用率的分阶段采样，
可以量化"长上下文 → KV 访存放大 → 昇腾算力空转"这一核心瓶颈在不同
优化方案下的缓解程度。
```

**8. 性能剖析（技术路线 step 1）—— 加入昇腾特异的 profiling 维度**

```latex
重点采集 HBM 读写量、AI Core 利用率和 KV Cache 传输时间的分阶段分解
数据，结合昇腾计算/访存比特征定位长文本 Decode 的访存瓶颈点。
```

**9. 预期目标 item 1 —— 加入上下文长度维度**

```latex
在不同上下文长度（4K--1M）下量化 KV 传输和 layout 转换在端到端延迟
中的占比。
```

## 修改原则总结（供 Codex 学习）

### 原则 1：研究点必须有递进关系，不能是并列的任务列表

错误写法：三个研究点 = 三个独立的技术任务（如"做 KV 传输"+"做动态 CP"+"做评估"）。

正确写法：每个研究点解决上一层留下的未解决问题，形成"基础设施 → 单节点优化 → 集群级优化"的递进链。

### 原则 2：每个研究点必须回答"为什么是昇腾"

不能写"面向昇腾的 XX 优化"但全文把"昇腾"替换成"GPU"后依然成立。必须在动机段说清楚：
- 这个瓶颈在昇腾上为什么比 NVIDIA 更严重？（回扣计算/访存比）
- 长上下文如何放大这个瓶颈？（回扣 KV Cache 规模公式中的 L）

### 原则 3：定性判断必须有定量锚点支撑

"昇腾计算/访存比较高"出现了三次，但没有一次给出数值或公式 → 评委认为你在回避具体数据。

正确的做法是：在全文最早出现的位置（选题背景）给出完整的数值对比和公式推导，后续引用时只需一句话回扣（如"如前所述，$L$ 越大 KV Cache 读取越主导 HBM 访问"）。

### 原则 4：开题报告不写元评论

以下句子都属于元评论，应从正文中删除：
- "本课题拟将现有工作压缩为三个研究点展开"（评委不需要知道你的章节设计过程）
- "这样既保留已有工程深度，又避免..."（自我评价）
- "该研究点对应 RFC Road Map 中的 XX 阶段"（内部项目管理信息，不属于学术论证）

### 原则 5：自己的前期工作用"本课题前期提出"，不用第三人称

如果是你自己的 RFC/论文/专利，用"本课题前期在 XX 中提出"或直接引用，不要写"某某在 XX 中提出"——这会让评委困惑"某某是谁？为什么你要做他的工作？"。

### 原则 6："已有科研基础"要写已完成的具体结果，不要写"已经分析/梳理/克隆"

错误："已克隆并分析 CP-Viz 项目"——clone 一个 repo 不是科研基础。

正确："前期 Decode 节点实验覆盖 4K、256K、512K 和 1M 上下文长度...在 1M、16 rps 条件下，dycp-dp 的 P90 TPOT 为 59.10 ms，P90 ITL 为 59.99 ms"——有具体数字的结果才是科研基础。

### 原则 7：融合算子是研究贡献，不是工程优化

`transpose_kv_cache_by_block` 融合算子不应被写成"我们把 copy 换成了 reshape"。应该写清楚：
- 它解决了什么问题（逐层多次 launch → 单次融合计算）
- 设计要点（利用 DataCopy 指令在 UB 内完成跨 head 数据重排，模板一/二的分情况处理）
- 收益数字（7ms → 0.24ms，TTFT 降低 90--110ms）

这样才能让评委理解这是一个有设计含量的算子，而不是换了个 API 调用。

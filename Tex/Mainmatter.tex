\section{选题的背景及意义}

\subsection{选题背景}

近年来，大语言模型已从通用对话逐步扩展到知识库问答、长文档理解、代码仓库分析、智能体任务规划等复杂场景，需要模型一次性处理数万到数十万 token 的上下文。长文本输入会显著增加首字延迟、显存占用、KV Cache 管理压力和多卡通信开销，使推理系统在吞吐、时延和资源利用率之间面临更复杂的权衡。更重要的是，长文本推理在昇腾等国产加速器上的瓶颈结构与 NVIDIA GPU 存在显著差异，面向 GPU 的优化方案不能直接迁移。

自回归大模型推理可分为 Prefill 和 Decode 两阶段。Prefill 阶段计算量随输入长度快速增长，通常表现为计算密集型，直接决定 Time To First Token（TTFT）；Decode 阶段逐 token 生成，受显存带宽和 KV Cache 访问效率主导，直接决定 Time Per Output Token（TPOT）。两阶段的资源特征明显不同，传统混合部署方式将 Prefill 和 Decode 放在同一组设备上，通过 continuous batching、PagedAttention、chunked prefill 等机制共调度\citep{kwon2023efficient}。这种方式在中短上下文下有效，但在长文本负载中容易暴露阶段间干扰：长 Prefill 插入 Decode 批次后导致 ITL 抖动，而 Decode 的低 TPOT 要求又限制 Prefill 批大小，使 TTFT 难以下降。两阶段对并行策略和批处理参数的最优配置也不一致，混合部署迫使系统采用折中策略，造成资源浪费。

Prefill-Decode 分离（PD 分离）正是针对上述问题提出的系统优化思路，它将 Prefill 和 Decode 分别部署在不同实例或集群上，请求由 P 实例完成长上下文编码后，将 KV Cache 传输到 D 实例继续生成。该架构的核心价值在于 P 和 D 可分别配置设备数量、并行策略和调度策略，使 TTFT 与 TPOT 相对独立优化；Decode 不再被长 Prefill 打断，有利于控制尾延迟。对于昇腾平台，PD 分离还具有更明确的适配意义：P 侧可通过更大 batch 和更高并行度利用 NPU 矩阵计算能力，D 侧围绕 KV Cache 访存和 PageAttention 进行优化，避免两阶段在昇腾特有的高计算/访存比下相互放大开销。

与此同时，即使采用 PD 分离，超长 prompt 的 Prefill 仍可能在单个并行组内产生很高的 TTFT，Decode 阶段随上下文增长也受 KV Cache 容量的限制。上下文并行（Context Parallelism，简称 CP）沿序列维度切分输入或 KV Cache，是解决长序列瓶颈的另一关键技术：Prefill Context Parallelism（PCP）将长输入切分到多设备并行以降低 TTFT；Decode Context Parallelism（DCP）将 KV Cache 按序列维度分片，减少冗余存储。

从硬件特征看，长文本推理优化还必须考虑不同加速器的计算/访存能力配比。昇腾 910 系列的 FP16 峰值算力与 HBM 带宽之比约为同代 NVIDIA GPU 的 1.5--2 倍，这意味着每单位 HBM 带宽需要支撑更多的计算操作，访存更容易成为系统瓶颈。这一差异在长上下文 Decode 阶段尤为关键。Decode 阶段每生成一个 token，需要从 HBM 读取模型权重（约 $2\times$ 参数量字节）和该请求的完整 KV Cache（约 $2 \times n_\text{layers} \times L \times n_\text{kv\_heads} \times d_\text{head}$ 字节，其中 $L$ 为当前上下文长度）。当 $L$ 增长至 128K 乃至 1M，KV Cache 读取量远超权重读取量，成为 HBM 访问的主导成分；此时昇腾高计算/访存比导致计算单元等待数据的时间占比更高，算力利用率更低。相比之下，Prefill 阶段以批量矩阵乘法为主，单次加载权重后可在大量 token 上复用计算，计算/访存比高的优势得以发挥。因此，昇腾长文本推理的瓶颈呈现出"Prefill 偏计算、Decode 偏访存"的两极分化，且上下文越长分化越剧烈。面向昇腾的优化需要因阶段施策：P 侧利用高算力加速长 prompt 的批量 Prefill 计算，D 侧则必须以削减 KV Cache 访存和 HBM 带宽压力为首要目标——通过 PD 分离隔离两阶段干扰，通过 PCP/DCP 沿序列维度分摊或去冗余 KV 存储，通过动态 CP 将超长请求的 KV 读取压力分散到多个设备。后续实验将通过 HBM 读写量、AI Core 利用率和 TTFT/TPOT 分解，量化昇腾与 NVIDIA 平台在长文本 Decode 瓶颈上的结构性差异。

\subsection{研究问题}

综上所述，要有效提升昇腾平台上大模型长文本推理的效率，必须攻克三个环环相扣的系统性问题：

第一，PD 分离后 KV Cache 的正确传输与布局适配问题。PD 分离要求 P 节点完成 Prefill 后将 KV Cache 交付 D 节点，但 P 侧与 D 侧的并行配置往往异构（P 侧高 TP、D 侧低 TP），TP/PP 异构导致 P 侧生成的 KV Cache 布局与 D 侧 PageAttention 所需布局不一致。对于 GQA/MHA/MQA 模型，KV head 随 TP rank 切分，D 节点若按默认路径拉取将出现 KV head 缺失或顺序错误；当 PP 和 MTP 共同启用时，层划分关系进一步复杂化。如何在昇腾平台上建立从源端布局到目标端布局的精确映射，并通过融合算子降低重排开销，是 PD 分离正确、高效运行的前提。

第二，Decode 节点在长短请求混部下的负载均衡问题。真实在线负载中，少量超长请求的 KV Cache working set 可达数 GB，当其集中落在某个 DP 副本上时，该副本每个 Decode step 都需遍历完整 KV Cache，在昇腾高计算/访存比下形成"访存 straggler"——同一 Domain 内其他副本因无数据可算而空转，尾部延迟拖慢整个 batch。静态 CP 又无法同时满足短请求的低开销和长请求的显存分摊需求。如何在 PD 分离 Decode 节点上实现请求级动态 CP 调度，使得短请求走轻量路径、长请求由多个副本协同处理，成为关键问题。

第三，Decode 集群的运行时弹性与存储效率问题。在线负载具有时间局部性和突发性，波峰需要更多 DP 副本分担解码压力，波谷闲置副本持续占用资源；同时 Decode 侧常以 TP=1 运行以规避 KV Cache 复制开销，但在高并发下又需要 TP 的计算吞吐，形成"不开 TP 算力不足、开 TP 显存放不下"的困境。如何在 Decode 集群层面实现 DP 的运行时动态扩缩容和 TP 域内的 KV Cache 去冗余，使资源规模匹配负载变化、存储效率突破 TP 复制瓶颈，是长文本推理服务在实际部署中的最后一环。

因此，本课题围绕上述三个问题展开研究：从传输正确性到节点内调度效率，再到集群层资源弹性，逐层推进。

\subsection{选题意义}

本课题选择“面向昇腾显卡的大模型长文本推理优化”作为研究方向，具有明确的理论意义和工程价值。一方面，昇腾 NPU 及其 CANN、Ascend Transformer Boost、MindIE、MindSpore/MindSpeed、vLLM-Ascend 等软件栈正在快速完善，已经支持 Continuous Batching、Page Attention、FlashDecoding、长序列、PD 分离、专家并行和上下文并行等关键能力\citep{mindie2026,vllmascendcp2026}。另一方面，昇腾平台在算子接口、KV Cache 布局、HCCL 通信、HCCS/RDMA 互联、AscendDirectTransport、运行时执行模式和量化格式等方面与 CUDA 生态存在差异，已有面向 GPU 的长文本推理优化方案不能直接迁移。尤其是在长上下文 Decode 阶段，昇腾高计算/访存比会放大 KV Cache 访存、block table 访问和跨卡同步带来的性能损失，使得 P/D 资源配比、KV 传输路径、D 侧 KV 布局和运行时调度成为影响端到端收益的关键因素。如何在昇腾平台上联合利用 PD 分离与 CP 并行，针对长文本负载设计阶段感知的资源配置、KV Cache 传输和调度策略，是提升国产 AI 加速器上大模型推理效率的重要问题。

从应用价值看，长文本推理优化直接影响大模型在科研文献分析、代码仓库理解、法律金融文档处理、企业知识库问答和智能体系统中的可用性。长上下文请求通常具有输入长、首字等待时间长、并发形态复杂、成本敏感等特点，如果缺少系统级优化，即使模型具备长上下文能力，也难以稳定支撑真实业务负载。从平台价值看，昇腾生态需要面向主流模型结构和真实服务场景的推理优化方法，尤其需要解决 PD 分离、CP 并行、TP/PP/EP 组合、KV Cache 传输和图模式执行之间的协同问题。本课题围绕这些问题开展研究，有助于形成面向国产 AI 加速器的大模型长文本推理优化经验。

因此，本课题拟围绕长文本推理中的两个核心瓶颈展开：其一，研究昇腾 PD 分离架构下 P 实例与 D 实例的资源配比、并行策略和 KV Cache 传输机制，使计算密集型 Prefill 尽可能消化昇腾高算力，使访存密集型 Decode 尽可能减少 HBM/KV 访问放大；其二，研究 CP 并行在 Prefill 和 Decode 阶段的适用方式，将长上下文沿序列维度分摊到多张昇腾设备上，缓解单设备显存与时延瓶颈。通过二者协同，有望在保证模型推理准确性的前提下，同时改善长文本场景下的 TTFT、TPOT、系统吞吐、显存利用率和服务稳定性。

本课题的优化路径围绕昇腾平台特有的瓶颈坐标系展开：横轴为上下文长度，决定 KV Cache 规模和访存压力；纵轴为阶段特征，Prefill 偏计算、Decode 偏访存；深度轴为硬件能力配比——昇腾高计算/访存比和相对较小的 HBM 容量使前两个维度的矛盾在长文本场景下剧烈放大。后续三个研究点分别对应这个坐标系中"传输效率""调度效率"和"存储效率"三个象限。

\section{国内外本学科领域的发展现状与趋势}

\subsection{大模型长文本推理服务优化研究}

大模型推理服务系统的早期优化主要集中在批处理调度、KV Cache 管理、算子融合和显存复用等方面。随着 Transformer 模型规模和上下文长度不断增加，KV Cache 已成为推理系统中的核心状态。PagedAttention 等方法借鉴操作系统分页思想，将 KV Cache 划分为固定大小的 block，并通过 block table 管理非连续缓存，从而降低显存碎片并提升多请求服务能力\citep{kwon2023efficient}。Continuous batching、prefix caching、chunked prefill、FlashAttention/FlashDecoding 等技术进一步提高了在线推理服务的吞吐和延迟表现\citep{dao2022flashattention,flashdecoding2023}。这些技术构成了当前大模型推理框架的基础能力，也是 PD 分离与 CP 并行进一步发挥作用的前提。

然而，长文本推理对系统提出了更强的要求。长上下文输入会放大 Prefill 阶段的计算开销，使 TTFT 从毫秒级或秒级上升到数秒甚至数十秒；同时，历史 KV Cache 随上下文长度和并发请求数线性增长，Decode 阶段的显存压力和访存开销显著增加。单纯依靠通用 batching 或显存管理技术，难以同时满足长输入低 TTFT、长输出低 TPOT、高吞吐和高并发。因此，近年来研究重点逐渐从单点算子优化转向面向推理阶段、序列维度和集群资源的系统级优化，其中 PD 分离和 CP 并行是最具代表性的两条路线。

\subsection{Prefill-Decode 分离研究现状}

国际上，PD 分离的思想首先由一系列工作系统化提出。Splitwise 最早指出 Prefill 和 Decode 分别呈现计算密集和访存密集特征，可部署在不同类型设备上\citep{patel2023splitwise}。DistServe 将其发展为面向 SLO 的系统架构，将两阶段分配到不同 GPU，分别针对 TTFT 和 TPOT 约束进行资源和并行策略协同优化，并考虑阶段间 KV Cache 传输带宽\citep{zhong2024distserve}。Mooncake 进一步从 KV Cache 视角构建分离式架构，利用 GPU 集群中未充分使用的 CPU、DRAM、SSD 等资源构建分层 KV Cache 存储，将 KV Cache 的生成、传输、缓存和调度纳入系统设计\citep{qin2024mooncake}——该工作表明长文本下 PD 分离的瓶颈会从计算迁移到 KV Cache 生命周期管理。开源推理框架方面，vLLM 已集成 disaggregated prefilling，vLLM-Ascend 进一步支持基于 Mooncake 的 PD 分离方案，包括 MooncakeConnector 和 MooncakeLayerwiseConnector\citep{vllmascendpd2026,vllmascenddeepseekpd2026}。国内方面，昇腾 MindIE 将 PD 分离作为关键特性，与 Continuous Batching、Page Attention、FlashDecoding 等机制协同使用；昇腾大规模专家并行方案将 P 和 D 部署在不同服务器上，通过高速互联传输 KV Cache，官方技术文章明确指出了混合部署下资源利用不足和阶段间干扰问题\citep{mindie2026,ascendpd2025,ascendexpert2026}。

总体来看，PD 分离已形成较清晰的技术共识：Prefill 和 Decode 具有不同资源特征，应在系统层面解耦。但现有研究在昇腾平台适配方面存在明显不足。首先，现有工作主要基于 NVIDIA GPU 和 CUDA 生态，其通信原语和缓存布局与昇腾平台差异显著。其次，PD 分离会引入额外 KV Cache 传输成本，当输入长度、P/D 比例或网络带宽变化时收益并不稳定，而昇腾高计算/访存比会进一步放大 KV 传输和 D 侧访存之间的压力耦合。当 D 侧的 KV Cache 拉取、layout 重排和 PageAttention 访问缺乏针对性优化时，昇腾有限的 HBM 带宽将同时承受三方面压力，P 侧节省的 TTFT 可能被 D 侧 TPOT 抖动完全抵消。更进一步，在 TP 异构场景下，P 侧生成的 KV Cache 布局与 D 侧 PageAttention 所需布局可能不一致（如 GQA 模型 KV head 随 TP rank 切分、PP 场景下层划分），PD 分离还需要处理 TP/PP 异构下的布局映射和运行时执行模式与通信路径之间的耦合。本文作者在昇腾框架适配过程中发现，vLLM-Ascend 的 MooncakeConnector 在处理 P/D 侧 TP 异构的 GQA/MHA 模型时，默认的 KV Cache 拉取路径不做 head 级别的重排序，直接导致推理精度异常；PP 与 MTP 的层切分冲突也是框架实现未覆盖的边界情况。因此，昇腾上的 PD 分离需要将阶段解耦、KV 传输、布局转换、通信拓扑和访存瓶颈作为整体来优化。

\subsection{上下文并行研究现状}

上下文并行的核心思想是沿序列维度切分长上下文，使一个请求的长序列计算分布在多个设备上完成。与数据并行按请求或样本划分、张量并行按隐藏维度或矩阵维度划分、流水并行按层划分不同，CP 直接针对长上下文本身进行切分，因此特别适合解决长 prompt 带来的单设备显存和时延瓶颈。

Ring Attention 是上下文并行方向的代表性工作之一。该方法采用 blockwise attention，将序列划分为多个 block，并通过环形通信在设备间传递 KV block，使每个设备可以在计算本地 attention 的同时与其他设备交换 KV 数据\citep{liu2023ringattention}。Ring Attention 的重要特点是保持精确注意力计算，不依赖稀疏化或近似剪枝，并通过通信与计算重叠来提升长序列可扩展性。它为后续长上下文训练和推理中的 ring-style CP 提供了基础思路。

DeepSpeed-Ulysses 则从另一条路径推动了序列并行发展。它通过沿序列维度切分输入，并利用 all-to-all 通信在注意力头维度和序列维度之间重排数据，从而支持极长序列 Transformer 训练\citep{jacobs2023deepspeedulysses}。Ulysses 方案在部分模型结构和网络条件下具有较高效率，但对 attention head 数量与并行度的可整除关系存在约束。后续 USP 等工作尝试统一 Ulysses 和 Ring Attention 两类方案，结合二者在通信模式、模型适配性和拓扑适配性上的优缺点，形成更通用的长序列并行方法\citep{fang2024usp}。昇腾 MindSpeed 的 Hybrid 长序列并行也采用融合 Ulysses 与 Ring Attention 的思路，以缓解单一方案在 GQA/MQA 模型和小序列块场景中的局限。

面向推理场景，Context Parallelism for Scalable Million-Token Inference 将 CP 明确用于长上下文大模型推理，并设计了 pass-KV 和 pass-Q 等精确 ring attention 变体，覆盖 full prefill、persistent KV prefill 和 decode 等用例\citep{zhong2024contextparallelism}。该工作在多节点 H100 集群上展示了长上下文 Prefill 的近线性扩展能力，说明 CP 不仅适用于训练，也可以成为长文本在线推理降低 TTFT 的关键手段。与此同时，Mnemosyne 等工作也围绕百万级上下文推理提出自适应 chunking、Sequence Pipeline Parallelism 和 KV Cache Parallelism 等策略，反映出长上下文推理正在从“能否放下”转向“能否高效服务”。

在昇腾生态中，vLLM-Ascend 已经提供 Context Parallel 支持，并将其划分为 PCP 和 DCP 两类。官方文档中，PCP 通过在 Prefill 阶段划分序列维度，让不同设备并行计算不同序列块，以降低长上下文请求的 TTFT；DCP 则在 Decode 阶段沿序列维度分片 KV Cache，减少 TP 域内的 KV 冗余存储，为更大 batch size 和更长上下文提供显存空间\citep{vllmascendcp2026}。vLLM-Ascend 文档还指出，CP 可以与 eager 模式、图模式、prefix cache、chunked prefill、MTP、PD 分离和 MLAPO 等功能协同使用。在官方 Ascend 910C/A3 环境示例中，DeepSeek-R1-W8A8 的 128K 输入在引入 PCP 后 TTFT 从 73.2s 降至 46.0s，Qwen3-235B 的 120K 输入 TTFT 从 33.9s 降至 22.7s，说明 CP 在昇腾长文本推理中已经具备实际优化价值。

CP 的工程实现还需要处理更细粒度的元数据和通信组问题\citep{cpviz2026}。PCP 需要在请求级别维护 query lengths、KV lengths、position ids 等序列属性；DCP 会改变 token 在各 rank 上的归属关系和 slot mapping，需通过 virtual block 管理跨设备 block。CP 优化的核心难点已从算法层面的序列切分延伸到推理框架内部的 block table、slot mapping 和通信组设计。

在此基础上，Dynamic Context Parallelism RFC \citep{vllmdynamiccp2025} 提出 request-level heterogeneous parallelism：短请求走常规 DP-attention 路径（CP=1），长请求由多个 DP-attention 副本协同执行（CP>1），通过 Domain 抽象和跨 DP 调度解决长短请求混部下的负载倾斜问题。该方向表明，CP 的研究重点正在从”能否切分长序列”转向”如何在真实负载中动态分配注意力计算和通信资源”。

不过，CP 在实际系统中也引入了新的复杂性。首先，CP 会改变 KV Cache 的存储与访问方式，需要 block table、slot mapping、cache interleave size 等机制配合；当 CP 与 PD 分离同时使用时，还必须考虑跨 P/D 节点的 KV Cache 传输格式和切分方式。其次，PCP 和 DCP 的收益并不对称：PCP 主要降低长 prompt 的 TTFT，而 DCP 主要节省 Decode 阶段 KV Cache 显存并提高 batch 能力，但也可能带来额外通信和小算子开销。再次，CP 与 TP、EP、DP、MoE、量化、图模式、prefix cache 等功能之间存在组合约束，尤其是在昇腾平台上需要满足具体算子、通信域和部署拓扑要求。然而，在昇腾平台上，DCP 的收益不仅体现在显存节省，更体现在 Decode 访存压力的削减。由于昇腾高计算/访存比放大了每次 Decode step 中 KV Cache 遍历的 HBM 带宽压力（前述 $L$ 越大、压力越大），将 KV Cache 按序列维度分片后，每个设备仅需访问其负责分片对应的 KV 数据，HBM 读取量随 CP 度近似线性下降。因此，DCP 在昇腾长上下文 Decode 中的作用不仅是"省显存"，更是"降访存"——用可控的跨卡通信换取 HBM 带宽压力的缓解，而这恰恰是对昇腾高计算/访存比短板的对症下药。由此引出一个新问题：如何根据请求的上下文长度在线选择 CP 度，使得 KV 访存压力、跨卡通信开销和显存占用三者之间取得平衡？

\section{课题主要研究内容、预期目标}

\subsection{课题主要研究内容}

本课题围绕三个递进的研究点展开：首先解决 PD 分离下 KV Cache 从 P 节点到 D 节点的正确传输与布局适配（传输正确性），然后在 Decode 节点内实现请求级动态 CP 调度以缓解跨副本负载倾斜（节点内调度效率），最后面向 Decode 集群实现运行时 DP 弹性和 TP 域 KV 去冗余（集群层资源效率）。三个研究点从"能传"到"能调度"再到"能弹性伸缩"，逐层推进。

\subsubsection{面向昇腾 PD 分离的 KV Cache 传输与布局适配}

PD 分离要求 Prefill 节点在完成长上下文计算后，将 KV Cache 交付给 Decode 节点继续生成。这一传输的数据量直接由上下文长度决定——以 Qwen3-235B 为例，128K 上下文的单请求 KV Cache 约数十 GB——而昇腾 P/D 节点间的 HCCL/HCCS 或 RDMA 链路带宽有限，KV 传输时间在端到端延迟中的占比随上下文长度线性增长。传输完成后，问题并未结束：P 侧与 D 侧的并行配置往往存在异构：P 侧倾向于高 TP 以加速长 prompt 计算，D 侧倾向于低 TP 以扩大 batch 能力和降低访存放大。这种 TP/PP 异构导致 P 侧生成的 KV Cache 布局与 D 侧 PageAttention 所需布局不一致。对于 DeepSeek 等 MLA 模型，TP 域内各 rank 持有全量 KV Cache，布局差异相对隐蔽；但对于 Qwen 等 GQA/MHA/MQA 模型，KV head 随 TP rank 切分——例如 Qwen3-235B 在 P 侧 TP=16 时，每 rank 仅持有 4 个 KV head 中的 1 个分片——D 节点若按默认路径拉取 KV Cache，将出现 KV head 缺失、顺序错误或本地 block 无法直接消费。当 PP 和 MTP 共同启用时，P 节点不同 PP stage 仅持有部分层的 KV Cache，层划分关系进一步复杂化：D 节点需要感知 P 侧的 PP stage 和 MTP 额外层，才能将 KV Cache 写入正确的层地址。

本研究点将上述问题抽象为 PD 分离场景下的 KV Cache 布局映射与高效转换问题，围绕 KV Connector 展开系统化设计。该 Connector 采用 D-pull 模式：由 D 节点按需从 P 节点拉取 KV Cache，而非 P 节点主动推送。选择 D-pull 的考量在于，昇腾 Decode 侧因高计算/访存比导致 HBM 带宽已高度紧张，由 D 侧按需拉取可在拉取过程中按目标 layout 直接写入 block，避免 P-push 模式下 D 侧额外开辟接收缓冲区的显存开销和一次额外的显存拷贝。具体设计包括：（1）使 Connector 感知 P/D 两侧 TP、PP 和 layer partition 配置，同时感知昇腾 HCCL/HCCS 互联拓扑中各 rank 之间的跳数和链路带宽差异，为每个 D rank 选择延迟最低的 P rank 或 P rank 集合作为 KV Cache 源端，建立从源端布局到目标端布局的映射关系——MLA 场景支持随机选择 P rank 以实现负载均衡，GQA 场景则根据 TP 切分关系精确匹配，并在跨机架拓扑中优先选择同一 HCCS ring 内的 P rank 以降低传输延迟；（2）在 KV Cache 传输完成后，按 block 粒度进行 split、cat 和 transpose，使其符合 D 节点本地 PageAttention 的 KV 排布；（3）明确 KV 拉取、重排序、D 节点 forward 和 P 节点显存释放之间的数据生命周期，保证 D 节点完成本地写入后再释放 P 侧缓存。当前已完成 GQA TP 异构、PP 层切分和 MTP 额外层场景下的布局映射与正确性验证。在该验证过程中，布局转换的开销瓶颈逐渐显现：当前实现使用 torch 原生 \verb|reshape| 和 \verb|transpose| 算子逐 block 对 KV Cache 做重排，每层每 block 均触发独立的 kernel launch。以 GQA 场景下 4K 上下文长度、4 个 KV head 的配置为例，单次重排的 torch 算子耗时约 50 ms，其中 kernel launch 开销和逐 block 显存搬运占主导。昇腾 NPU 提供的 \verb|_npu_reshape_and_cache| 算子可在单次调用内完成 block 粒度的数据搬运和 layout 重排，初步 benchmark 表明该算子可将耗时降至约 7 ms（图~\ref{fig:reshape-benchmark}），相比 torch 降低约 7 倍。但 7 ms 在端到端 Decode 路径中仍不可忽略。在 PD 分离的同步调度模式下，reshape 计算可与前一个 Decode step 的 attention 部分重叠，利用调度 bubble 掩盖其开销。然而随着异步调度和 pipeline 通信隐藏技术的引入，调度 bubble 持续被压缩，reshape 算子将暴露在 Decode 的 critical path 上，使原本被 bubble 掩盖的开销直接转化为 ITL。为此，后续需进一步设计 \verb|transpose_kv_cache_by_block| 等融合算子，将 layout 转换直接并入 PageAttention 的读写路径，使这部分开销收敛至微秒级并在端到端延迟中降至可忽略水平。该研究点是 PD 分离在昇腾平台上正确、高效运行的基础设施，也是后续动态 CP 能够稳定工作的前提。

\subsubsection{面向 Decode 节点的动态 CP 与跨 DP 调度}

真实在线负载通常包含大量短请求和少量超长请求。这一分布特性在昇腾平台上会触发一种特定的"访存 straggler"效应：一个超长请求的 KV Cache working set 可达数 GB，若集中落在某个 DP 副本上，该副本每个 Decode step 都需从 HBM 遍历完整 KV Cache——在昇腾高计算/访存比下，访存时间主导 ITL，而同一 Domain 内其他 DP 副本的计算单元因无数据可算而空转。此时，空转副本的算力不仅未能提升吞吐，反而因为 straggler 副本的尾部延迟拖慢了整个 batch。静态 CP 若按长请求统一配置，短请求将承担不必要的跨卡通信开销；若按短请求配置，单个长请求的 KV 访存瓶颈无法缓解。本课题前期在 Dynamic Context Parallelism RFC \citep{vllmdynamiccp2025} 中提出了 request-level heterogeneous parallelism：短请求走常规 DP-attention 路径（CP=1），长请求由多个 DP-attention 副本协同处理（CP>1），并通过 Domain、CrossDPScheduler、CrossDPKVCacheManager、batch 重排以及 attention score/LSE 聚合支持跨 DP 动态 CP。RFC Road Map 进一步提出两档 CP 粒度、多档 CP 粒度、通过 KV Connector 支持运行时 CP 调整、支撑 1M 上下文等阶段目标。

本研究点聚焦 PD 分离架构中的 Decode 节点，将上述 RFC 设计在昇腾平台上完成原型实现与性能评估。Scheduler 根据 Decode 上下文长度、D 节点 KV Pool 占用和并发压力，为请求选择常规 DP 路径或跨 DP 协同路径；Domain 将多个 DP-attention 副本组织成可协同处理长上下文请求的资源域；CrossDPKVCacheManager 维护跨 DP 的 block pool、slot mapping 和 virtual block；Attention backend 在 Decode 单 token 场景下聚合各 DP rank 的 attention score 和 LSE，保证输出一致性。前期在昇腾 910B 集群上完成 Decode 节点实验，覆盖 4K、256K、512K 和 1M 上下文长度以及 1--16 rps 负载，HBM 带宽约 1.5 TB/s。在 1M、16 rps 条件下，dycp-dp 的 P90 TPOT 为 59.10 ms，P90 ITL 为 59.99 ms，明显优于静态 dcp 的 77.31 ms 和 84.32 ms，也远优于 pcp-16 接近 300 ms 的尾部延迟，说明动态 CP 能有效缓解昇腾 Decode 阶段的 KV 访存压力和长尾抖动。

在 PD 分离与 GQA reshard 联合配置下，以 Qwen3-235B 模型在昇腾 910B 上测试，Prefill 侧配置 TP=16，Decode 侧配置 DP=32，输入 4K token、输出 1.5K token。端到端平均 TPOT 从 colocated 部署的 120 ms 降至 PD 分离后的 92 ms，收益主要来自 PD 分离消除阶段间干扰并使 P/D 各自选择最优并行度，以及 GQA reshard 保证 D 侧 KV Cache layout 正确可消费。该结果表明，仅启用 PD 分离与 GQA reshard 即可在小 batch 场景下获得约 23\% 的 TPOT 改善，为 DyCP 的进一步优化提供了有效的基线。

该研究点的增量贡献在于：将 RFC 中与硬件无关的调度架构在昇腾平台的 AscendDirectTransport、HCCL 通信域和推理运行时上完成系统实现，并针对昇腾高计算/访存比下 Decode 访存瓶颈更突出的特点，验证了动态 CP 在昇腾平台上的收益边界与适用条件。

\subsubsection{面向 Decode 集群的运行时 DP 动态扩缩容与 DCP 感知调度}

研究点 1 和研究点 2 分别解决了 PD 分离的 KV 传输正确性和 Decode 节点的请求级负载均衡问题，但 Decode 集群在真实在线服务中仍面临两个运行时适配挑战。其一，在线负载具有明显的时间局部性和突发性——波峰时段请求排队深度增加，需要更多 DP 副本分担解码压力；波谷时段闲置副本持续占用显存和功耗——而现有系统的 DP 资源配置通常是静态的，无法根据负载动态伸缩。其二，Decode 侧 KV Cache 随上下文长度线性增长，在昇腾有限的 HBM 容量下长上下文请求的 batch 能力受限。DCP 通过在 Decode 侧沿序列维度分片 KV Cache，已被验证可有效减少单设备上的 KV 冗余存储、降低每个 Decode step 的 HBM 读取量，但对长短请求混部的场景，固定 DCP 度仍会导致短请求承担不必要的跨卡通信开销。

本研究点面向上述挑战，在 DyCP 框架内集成两项机制。（1）Decode 运行时 DP 动态扩缩容：基于 RFC Road Map Final Release 中 Dynamic Domain Instantiation 和 Within-Domain Dynamic DP Load Balancing 的设计，在 Decode 集群中实现 DP 副本的运行时增减——当监测到请求排队深度或 KV Pool 压力超过阈值时，动态实例化新的通信域（Domain）并挂载 DP 副本分担负载；当负载回落时，通过长尾请求迁移将待回收副本上的请求逐步迁出，回收闲置副本并释放对应显存。关键技术问题包括：通信域的运行时构建与销毁开销、Domain 内 DP 副本间的负载均衡策略、扩缩容触发阈值的自适应选择，以及扩缩容过程中正在进行的 Decode step 的连续性保证。（2）DCP 感知的请求级调度：在 DyCP 的请求调度中引入 DCP 维度——Scheduler 在选择 CP 粒度时，不仅考虑请求的上下文长度，还将 DCP 分片所带来的显存节省和 HBM 带宽削减纳入收益评估，使短请求仍走 CP=1 路径，长请求在通过 DCP 分片降低单 rank 访存压力后由多个 DP 副本协同处理。该机制需要与 block table、slot mapping 和 PageAttention 访存路径协同设计：每个请求的 KV Cache 按 DCP 分片写入对应 rank，Decode attention 计算时通过 DCP all-gather 获取跨 rank KV 数据。关键技术问题包括：DCP 分片粒度与 DyCP 跨 DP 调度粒度的匹配、DCP all-gather 通信对 ITL 的影响控制，以及与 PD 分离 KV Connector 的交互（P 侧传输的全量 KV Cache 需按 DCP 分片方式写入各 rank）。两项机制共同使 Decode 集群具备运行时弹性与存储效率，将 RFC Road Map Final Release 中的关键能力在昇腾平台上落地验证。

\subsection{预期目标}

本课题预期形成一套面向昇腾显卡的大模型长文本推理优化方法，并在真实模型和真实推理框架中进行验证。具体目标包括：

\begin{enumerate}
    \item 完成面向昇腾 PD 分离的 KV Cache 传输与布局适配，支持 GQA、MHA、MQA、TP 异构和 PP/MTP 场景；在不同上下文长度（4K--1M）下量化 KV 传输和 layout 转换在端到端延迟中的占比，并通过融合算子将重排开销控制在可忽略水平。
    \item 完成 PD 分离 Decode 节点上的动态 CP 调度与评估，支持根据上下文长度、KV Cache 占用和 D 节点负载选择不同 CP 粒度，缓解跨 DP 副本负载倾斜和长尾 ITL 抖动。
    \item 完成 Decode 集群运行时 DP 动态扩缩容与 TP 域 KV Cache 去冗余机制：前者使 Decode 集群能够根据在线负载动态调整 DP 资源规模，后者在 Decode 开启 TP 时通过 DCP 消除 KV 冗余副本，提升显存效率与系统弹性。
\end{enumerate}

\section{拟采用的研究方法、技术路线、实验方案}

\subsection{技术路线}

本课题的技术路线按”瓶颈量化 → 传输适配 → 请求级调度 → 集群级弹性”四个阶段推进，与研究内容一一对应，但侧重于方法论的递进。

\begin{enumerate}
    \item 瓶颈量化阶段：在昇腾环境中部署典型长文本模型，在不同上下文长度（4K 至 1M）下测量混合部署、PD 分离、静态 CP 和动态 CP 配置的 TTFT、TPOT、ITL、吞吐和显存占用，重点采集 HBM 读写量、AI Core 利用率和 KV Cache 传输时间的分阶段分解数据。这一阶段的目标不是验证方案，而是通过分解 TTFT 和 TPOT 的构成，量化”长上下文 → KV 访存放大 → 昇腾算力空转”这一核心瓶颈，为后续优化提供基线和切入点。
    \item 传输适配阶段：围绕 Mooncake Connector 或类似 KV Connector，完成 TP 异构、PP/MTP 层切分和 KV Cache 布局转换，使 P 节点生成的 KV Cache 能被 D 节点正确高效消费。该阶段重点解决 PD 分离”能否正确传”的问题，通过融合算子降低 layout 转换开销，确保 KV 传输和重排不成为端到端延迟的主导项。
    \item 请求级调度阶段：在传输正确性得到保证的基础上，基于 Dynamic Context Parallelism RFC \citep{vllmdynamiccp2025} 中的 Domain、CrossDPScheduler、CrossDPKVCacheManager 和 attention 聚合思路，在 PD 分离 Decode 节点实现请求级 CP 粒度选择和跨 DP 协同调度。该阶段核心方法是”诊断 → 决策 → 执行”：Scheduler 监测请求上下文长度和 DP 副本负载，选择常规路径或跨 DP 协同路径，并在运行时调整以减少长尾抖动。
    \item 集群级弹性阶段：在节点级动态 CP 之上，进一步实现 Decode DP 运行时动态扩缩容和 TP 域 DCP KV 去冗余。该阶段的技术路线是”弹性 + 存储效率”两条线并行：扩缩容方面，通过 Dynamic Domain Instantiation 和 Domain 内负载均衡实现资源规模随负载变化；KV 去冗余方面，利用 DCP 使 TP 域各 rank 仅持有 KV Cache 分片而非全量副本。两项机制的共同目标是使 Decode 集群在资源效率和弹性上匹配在线负载的时间局部性。
\end{enumerate}

\subsection{实验方案}

实验模型方面，拟选择昇腾生态中已适配或正在适配的典型长上下文模型，如 Qwen 系列、DeepSeek 系列等，覆盖 MLA、GQA、MHA 或 MQA 等不同注意力结构。实验平台方面，拟基于昇腾 910 系列或实验室可用昇腾集群，使用 CANN、torch-npu、vLLM-Ascend、MindIE 或相关推理框架完成部署；在条件允许时，选取 NVIDIA GPU 平台作为对照，用于展示两类硬件在计算/访存比、HBM 访问压力和长文本 Decode 瓶颈上的差异。实验负载方面，Decode 节点已完成 4K、256K、512K、1M 上下文长度和 1--16 rps 负载下的 dycp-dp、dcp、pcp/pcp-16 对比；后续将补充三组实验：DP 动态扩缩容实验（模拟波峰/波谷负载切换，测量扩缩容延迟、归一化 QPS 变化和显存回收效果）、TP 开启后 DCP KV 去冗余实验（对比启用/不启用 DCP 的显存占用和 ITL 分布），以及 P/D 配比和长短请求混合比例实验。

对比基线包括：未启用 PD 分离的混合部署方案、启用 PD 分离但未针对 TP 异构优化的方案、启用通用 KV Cache 重排序的方案、启用静态 PCP/DCP 的单独优化方案、启用固定 CP 粒度的跨 DP 方案，以及本课题提出的融合 PD 分离 KV 传输、Decode 动态 CP 与运行时 DP 扩缩容的优化方案。评价指标包括 TTFT、TPOT、ITL P50/P90/P95/P99、归一化 QPS、显存峰值、HBM 读写量及带宽利用率、AI Core 利用率、KV Cache 传输时间、layout 转换时间、算子 launch 次数、跨 DP 负载均衡程度和推理输出一致性等。特别地，通过 HBM 读写量随上下文长度的变化曲线和 AI Core 利用率的分阶段采样，可以量化"长上下文 → KV 访存放大 → 昇腾算力空转"这一核心瓶颈在不同优化方案下的缓解程度。

\section{可行性分析}

本课题具有较好的可行性。首先，PD 分离、CP 并行、PagedAttention、Mooncake Connector 等机制已经在论文系统和开源框架中形成基础实现，为本课题提供了明确的技术起点。其次，昇腾平台已具备 CANN、HCCL、AscendDirectTransport、vLLM-Ascend、MindIE 等软件栈能力，能够支撑多卡推理、KV Cache 传输和长上下文实验。再次，前期材料中已经对 PD 分离场景下的 KV Cache 传输、GQA TP 异构重排序、PP/MTP 层划分和融合算子优化进行了初步分析，说明本课题的问题具有真实工程来源，研究路径较为清晰。

同时，本课题也存在一定挑战。KV Cache 布局受模型结构、并行方式和框架实现共同影响，错误的映射关系会直接导致推理精度异常；PD 分离和 CP 并行同时启用时会增加通信和同步复杂度；动态 CP 还会引入跨 DP block pool 管理、请求迁移、通信组选择和运行时调度粒度等新问题；DP 动态扩缩容和 TP 域 KV 去冗余则进一步增加了通信域运行时构建、跨 rank KV 分片一致性和扩缩容过程中 Decode 连续性保证的复杂度。针对这些挑战，本课题采用渐进式实现策略：先在 Decode 节点完成动态 CP 与静态 DCP/PCP 的可测对比，再实现 DP 动态扩缩容与 KV 去冗余机制；先优化显式可测的 KV Cache 传输和重排序开销，再逐步推进运行时弹性与端到端稳定性验证。

\section{已有科研基础与所需的科研条件}

\subsection{已有科研基础}

本课题已有较充分的前期基础。前期调研已经梳理了 Splitwise、DistServe、Mooncake、Ring Attention、DeepSpeed-Ulysses、Context Parallelism for Scalable Million-Token Inference 等代表性工作，明确了 PD 分离和 CP 并行在长文本推理中的作用边界。工程方面，已分析并改造 vLLM-Ascend 中 Mooncake Connector 在 PD 分离场景下的 KV Cache 传输流程，识别了 DeepSeek MLA 模型与 Qwen GQA/MHA/MQA 模型在 TP 域内 KV Cache 一致性方面的差异，并完成 GQA TP 异构、PP/MTP 层划分和 KV Cache 重排序等核心问题的初步设计与实现。

此外，已分析 CP-Viz 项目中的 CP 可视化材料，对 PCP/DCP 与 TP 组合后的 rank layout、slot mapping 和 virtual block 管理建立了直观理解，为本课题设计 PD+CP 下的 KV Cache 传输策略提供了参考。

同时，已在 vLLM 社区提出 Dynamic Context Parallelism RFC \citep{vllmdynamiccp2025}，该 RFC 中 Domain 抽象、跨 DP 调度和 attention 聚合等设计，与本课题关注的 PD 分离和昇腾运行时适配具有直接关联。在此基础上，已在 PD 分离 Decode 节点完成 dycp-dp 原型和评估：在 512K 与 1M 长上下文场景中，dycp-dp 相比静态 dcp 和 pcp-16 能显著降低 P90 TPOT 与 P90 ITL，1M、16 rps 条件下 P90 ITL 控制在约 60 ms，说明该方案对昇腾长文本 Decode 具有实际优化效果。

在具体技术问题上，前期工作已经取得以下阶段性进展：第一，GQA TP 异构场景下，D 节点能够从正确的 P rank 拉取 KV Cache，并在本地 block 内完成重排序；第二，PP 场景下能够根据 P 节点 PP stage 分组拉取不同层的 KV Cache，并写入 D 节点对应地址；第三，MTP 开启后通过显式配置 layer partition 解决默认层划分函数无法感知额外层的问题。上述基础表明，本课题并非从零开始，而是在已有系统实现和验证结果基础上继续完成实验闭环、消融分析和论文整理。

\subsection{所需科研条件}

本课题所需科研条件主要包括硬件平台、软件环境、模型与数据集以及性能分析工具。硬件方面，需要具备多张昇腾 NPU 的服务器或集群环境，并尽可能具备高速互联能力，以支持 PD 分离、CP 并行和跨节点 KV Cache 传输实验。软件方面，需要安装匹配版本的 CANN、驱动固件、torch-npu、vLLM-Ascend、MindIE 或相关推理框架，并具备编译和调试自定义算子的环境。模型方面，需要准备 DeepSeek、Qwen 等具有代表性的长上下文模型及其量化版本，以覆盖 MLA、GQA/MHA/MQA 等注意力结构。工具方面，需要使用日志、profiling、显存监控、通信监控和 benchmark 工具采集 TTFT、TPOT、QPS、显存和算子开销等指标。

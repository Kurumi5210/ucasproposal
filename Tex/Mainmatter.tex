\section{选题的背景及意义}

\subsection{选题背景}

近年来，大语言模型已从通用对话逐步扩展到知识库问答、长文档理解、代码仓库分析、智能体任务规划等复杂场景，需要模型一次性处理数万到数十万 token 的上下文。长文本输入会显著增加 TTFT、显存占用、KV Cache 管理压力和多卡通信开销，使推理系统在吞吐、时延和资源利用率之间面临更复杂的权衡。更重要的是，长文本推理在昇腾等国产加速器上的瓶颈结构与 NVIDIA GPU 存在显著差异，面向 GPU 的优化方案不能直接迁移。

Transformer 架构和大规模自回归语言模型奠定了当前大模型服务的基础\citep{vaswani2017attention,brown2020language}；随后 LLaMA、Qwen、DeepSeek 等开源或开放权重模型不断扩大参数规模、上下文窗口和模型结构复杂度\citep{touvron2023llama,touvron2023llama2,dubey2024llama3,yang2024qwen2,yang2025qwen25,deepseekai2024deepseekv2,deepseekai2025deepseekv3,deepseekai2025deepseekr1}。这些模型普遍采用 RoPE、GQA/MQA、MoE、MLA 或量化等结构与部署技术，使长上下文推理从单一注意力计算问题演化为模型结构、KV Cache、并行策略和硬件访存能力共同决定的系统问题。

表~\ref{tab:ctx-kvcache-evolution} 梳理了自 GPT-3 时代以来主流模型的上下文长度和 KV Cache 格式演进。这些数据汇聚为一个核心结论：

\textbf{压缩追不上扩张：KV 格式优化被上下文窗口增长抵消。}将压缩比与扩张比放在同一坐标系下对比，这一矛盾更加清晰。以百 B 级模型为例，KV 格式从 MHA 演进到 MLA 实现了约 34$\times$ 的每 token 压缩（LLaMA 65B MHA 的 2,560 KB/token $\to$ DeepSeek-V2 236B MLA 的 68 KB/token），但同期上下文窗口从 GPT-3 的 2K 扩张到当前主流的 128K——仅窗口扩张就贡献了 64$\times$ 的增长。结果是：DeepSeek-V3 在 128K MLA 下的单请求 KV Cache 约 10 GB，几乎被拉回到 GPT-3 175B 在 2K MHA 下的 9 GB 水平；若上下文进一步扩张至 1M，即使 MLA 也需约 60 GB 单请求 KV Cache。换言之，压缩进步被窗口扩张所抵消——每 token 开销的下降只是延缓了 KV Cache 总量的增长斜率，并未改变其随上下文长度线性增长的根本趋势。闭源模型（Claude Opus 4.6/4.7、Gemini 1.5 Pro）已支持 1M 上下文，Llama 4 等下一代开源模型也在向 1M 靠拢，这意味着仅靠 KV Cache 格式压缩不足以消化上下文增长，必须在系统架构层面引入 PD 分离、CP 并行和 KV Cache 层级存储等协同优化。

自回归大模型推理可分为 Prefill 和 Decode 两阶段。Prefill 阶段计算量随输入长度快速增长，通常表现为计算密集型，直接决定 Time To First Token（TTFT）；Decode 阶段逐 token 生成，受显存带宽和 KV Cache 访问效率主导，直接决定 Time Per Output Token（TPOT）。两阶段的资源特征明显不同，传统混合部署方式将 Prefill 和 Decode 放在同一组设备上，通过 continuous batching、PagedAttention、chunked prefill 等机制共调度\citep{kwon2023efficient}。这种方式在中短上下文下有效，但在长文本负载中容易暴露阶段间干扰：长 Prefill 插入 Decode 批次后导致 ITL 抖动，而 Decode 的低 TPOT 要求又限制 Prefill 批大小，使 TTFT 难以下降。两阶段对并行策略和批处理参数的最优配置也不一致，混合部署迫使系统采用折中策略，造成资源浪费。

Prefill-Decode 分离（PD 分离）正是针对上述问题提出的系统优化思路，它将 Prefill 和 Decode 分别部署在不同实例或集群上，请求由 P 实例完成长上下文编码后，将 KV Cache 传输到 D 实例继续生成。该架构的核心价值在于 P 和 D 可分别配置设备数量、并行策略和调度策略，使 TTFT 与 TPOT 相对独立优化；Decode 不再被长 Prefill 打断，有利于控制尾延迟。对于昇腾平台，PD 分离还具有更明确的适配意义：P 侧可通过更大 batch 和更高并行度利用 NPU 矩阵计算能力，D 侧围绕 KV Cache 访存和 PageAttention 进行优化，避免两阶段在昇腾特有的高计算/访存比下相互放大开销。

与此同时，即使采用 PD 分离，超长 prompt 的 Prefill 仍可能在单个并行组内产生很高的 TTFT，Decode 阶段随上下文增长也受 KV Cache 容量的限制。上下文并行（Context Parallelism，简称 CP）沿序列维度切分输入或 KV Cache，是解决长序列瓶颈的另一关键技术：Prefill Context Parallelism（PCP）将长输入切分到多设备并行以降低 TTFT；Decode Context Parallelism（DCP）将 KV Cache 按序列维度分片，减少冗余存储。

从硬件特征看，长文本推理优化还必须考虑不同加速器的计算/访存能力配比。昇腾 910B 的 FP16 峰值算力约为 320 TFLOPS，HBM 带宽为 1.2 TB/s，算力与带宽之比约为 267 TFLOPS/TB/s；作为对比，NVIDIA H100 SXM 的 FP16 稠密算力约为 494 TFLOPS，HBM 带宽为 3.35 TB/s，算力与带宽之比约为 148 TFLOPS/TB/s。昇腾 910B 每 TB/s 带宽需支撑的算力约为 H100 的 1.8 倍，意味着每单位 HBM 带宽需要支撑更多的计算操作，访存更容易成为系统瓶颈。这一差异在长上下文 Decode 阶段尤为关键。Decode 阶段每生成一个 token，需要从 HBM 读取模型权重（约 $2\times$ 参数量字节）和该请求的完整 KV Cache（约 $2 \times n_\text{layers} \times L \times n_\text{kv\_heads} \times d_\text{head}$ 字节，其中 $L$ 为当前上下文长度）。当 $L$ 增长至 128K 乃至 1M，KV Cache 读取量远超权重读取量，成为 HBM 访问的主导成分；此时昇腾高计算/访存比导致计算单元等待数据的时间占比更高，算力利用率更低。相比之下，Prefill 阶段以批量矩阵乘法为主，单次加载权重后可在大量 token 上复用计算，计算/访存比高的优势得以发挥。因此，昇腾长文本推理的瓶颈呈现出"Prefill 偏计算、Decode 偏访存"的两极分化，且上下文越长分化越剧烈。这一硬件特异的瓶颈结构决定了单一优化手段难以同时兼顾两阶段：算子级优化和 KV Cache 压缩可以降低每 token 访存开销，但无法解决超长上下文的单请求 KV Cache 总量问题；通用 batching 调度可以在短上下文负载下提高吞吐，但无法消除长 Prefill 插入 Decode 批次造成的延迟抖动。因此，必须在系统架构层面同时引入两阶段解耦（PD 分离）和序列维度切分（CP 并行），从"隔离干扰"和"分摊压力"两个方向协同应对。

面向昇腾的优化需要因阶段施策：D 侧必须以削减 KV Cache 访存和 HBM 带宽压力为首要目标——通过 PD 分离隔离两阶段干扰，通过 PCP/DCP 沿序列维度分摊或去冗余 KV 存储，通过动态 CP 按上下文长度和负载在 DP 与全量 CP 之间自适应选择，从而弹性分摊长上下文 Decode 的 KV 读取压力。后续实验将通过 HBM 读写量、AI Core 利用率和 TTFT/TPOT 分解，量化昇腾与 NVIDIA 平台在长文本 Decode 瓶颈上的结构性差异。

在上述通用长上下文推理瓶颈之上，MoE 架构的广泛采用进一步加剧了问题的复杂性。当前主流大模型中，DeepSeek-V2/V3/R1、Qwen-MoE、Mixtral 等均采用 MoE 结构，以较少的激活参数获得更大的模型容量。然而，MoE 层在 Decode 阶段引入 all-to-all 通信——同一同步组内的所有 DP 副本必须在 all-to-all 入口对齐后才能进行专家路由分发。这意味着任何副本间的 KV Cache 负载不均衡不仅会导致 straggler，还会在 all-to-all 同步点形成等待放大效应（即 MoE bubble）。昇腾 910B 的 HBM 带宽仅为 H100 的约 1/3，相同负载差异产生的 HBM 读取时间差被成倍放大，使 MoE bubble 在昇腾上远比 GPU 平台严重。因此，如何针对昇腾平台缓解 MoE bubble，构成本课题的核心应用场景。

\subsection{研究问题}

围绕昇腾平台长上下文推理的核心瓶颈——高计算/访存比放大 KV Cache 负载不均，在 MoE 模型的 all-to-all 同步点形成 bubble——本课题以动态 CP 协同执行为中心，研究三个逐层支撑的问题：

\textbf{核心问题（动态 CP 协同执行）：}昇腾 910B 单卡 HBM 容量有限，超长请求（如 128K 以上上下文）的 KV Cache 可达数十 GB，超出单副本显存容量，请求无法执行；即使能放入显存，单副本 HBM 带宽遍历完整 KV Cache 的时间远超 SLO。CP 通过多副本分片可同时解决容量和带宽问题，但静态 CP 对所有请求统一启用分片，在昇腾上因 HCCS 带宽有限，高负载时通信代价反超访存收益。能否在运行时根据请求上下文和负载强度自适应触发 CP——超长请求启用多副本协同消除 MoE bubble 并突破单卡显存限制，短请求保持单副本避免不必要通信？

\textbf{支撑问题一（数据通路——跨节点 KV Cache 传输与布局适配）：}PD 分离下，P 侧生成的 KV Cache 需经跨节点传输到达 D 侧。昇腾上这一传输面临两个独立挑战：其一，P/D 两侧 TP/PP 配置常常异构（P 侧倾向高 TP 加速 Prefill，D 侧倾向低 TP 扩大 batch），对 GQA/MHA 模型，KV head 随 TP rank 切分，异构拉取将导致 KV head 缺失或顺序错误——这是 PD 分离自身的正确性问题，不依赖 CP 也存在。其二，动态 CP 将 KV Cache 分片到多个 D 副本，若传输 layout 错位，分片会把错误扩散到全部参与副本——这是 CP 对数据通路提出的额外要求。此外，昇腾 D 侧 HBM 带宽紧张，传输后的 layout 转换若低效将直接推高 TPOT。能否在保证传输正确性的同时，通过 NPU 原生算子与融合算子将 layout 转换开销压缩至可忽略水平，使数据通路既满足 PD 分离的基本正确性，又为动态 CP 提供可靠的分片数据基础？

\textbf{支撑问题二（CP 的决策基线——副本负载感知）：}动态 CP 需要判断何时触发——如果所有请求都开 CP，通信代价不可控；如果都不开，超长请求形成 MoE bubble。触发决策需要一个基线：常规路径下目标副本如何选择，该副本当前负载是否满足请求的 SLO？现有调度器按请求数做负载均衡，在昇腾上存在错配——决定延迟的是 KV Cache 访问量而非请求数。能否以 KV usage 为指标感知副本负载，为 CP 触发提供可靠的决策基线？

三个问题形成"数据通路 → 决策基线 → 动态协同"的支撑关系：问题一解决 PD 分离下 KV 传输的正确性与效率（对 CP 额外提供可靠的分片数据基础），问题二提供 CP 触发的负载判断依据，核心问题在此基础上实现动态 CP 协同执行，消除 MoE bubble 并突破单卡显存限制。

\subsection{选题意义}

本课题的应用价值在于：长上下文推理直接影响大模型在科研文献分析、代码仓库理解、法律金融文档处理等场景中的可用性——长请求首 token 等待时间长、并发形态复杂、成本敏感，缺少系统级优化难以稳定支撑真实业务负载。平台价值在于：昇腾生态在算子接口、KV Cache 布局、HCCS/RDMA 互联和运行时执行模式等方面与 CUDA 生态存在差异，面向 GPU 的优化方案无法直接迁移。本课题以动态 CP 消除昇腾 MoE 推理的 bubble 为核心，以 KV Cache 跨节点传输和负载感知调度为支撑——三者协同有望在保证推理精度的前提下改善长文本场景的 TTFT、TPOT 和吞吐，为国产 AI 加速器上大模型推理优化的工程实践提供参考。

本课题的优化路径围绕昇腾长上下文推理的 KV Cache 访存瓶颈展开：核心是以动态 CP 缓解 HBM 带宽压力（对 MoE 模型额外消除 all-to-all bubble），数据通路和决策基线分别从传输正确性和负载感知两个维度支撑动态 CP 的落地。后续三个组件分别对应 KV Cache 跨节点传输（数据通路）、基于 KV usage 的负载感知（决策基线）和动态 CP 协同执行（核心机制）。此外，P/D 资源配比（P 实例与 D 实例的数量比及各自的并行配置）直接影响 PD 分离的端到端收益，但其最优值受模型结构、上下文长度分布和硬件拓扑共同影响，难以作为独立研究问题求解；本课题将其作为实验参数，在不同 P/D 配比下评估优化效果，并在实验方案中给出经验性配比建议。

\section{国内外本学科领域的发展现状与趋势}

\subsection{大模型长文本推理服务优化研究}

大模型推理服务系统的早期优化主要集中在批处理调度、KV Cache 管理、算子融合和显存复用等方面。随着 Transformer 模型规模和上下文长度不断增加，KV Cache 已成为推理系统中的核心状态。PagedAttention 等方法借鉴操作系统分页思想，将 KV Cache 划分为固定大小的 block，并通过 block table 管理非连续缓存，从而降低显存碎片并提升多请求服务能力\citep{kwon2023efficient}。Continuous batching、prefix caching、chunked prefill、FlashAttention/FlashDecoding 等技术进一步提高了在线推理服务的吞吐和延迟表现\citep{dao2022flashattention,flashdecoding2023}。这些技术构成了当前大模型推理框架的基础能力，也是 PD 分离与 CP 并行进一步发挥作用的前提。

从模型和算法层看，长上下文能力的提升主要来自三类路线：一是稀疏或局部注意力结构，如 Longformer 将长文档注意力复杂度降为近似线性\citep{beltagy2020longformer}；二是位置编码外推和窗口扩展，如 ALiBi、Position Interpolation 与 YaRN 改善模型对超出训练长度序列的泛化\citep{press2021train,chen2023extending,peng2023yarn}；三是面向无限上下文或流式场景的记忆机制，如 StreamingLLM 和 Infini-attention 通过保留 attention sink 或压缩记忆降低长序列服务开销\citep{xiao2023streamingllm,munkhdalai2024leave}。不过，长上下文窗口本身并不等价于稳定使用长上下文，Lost in the Middle 和 LongBench 等评测表明，模型对长输入中部信息的利用和跨任务稳定性仍然存在明显差异\citep{liu2023lost,bai2023longbench}。

从推理算子和 KV Cache 结构看，FlashAttention-2 进一步优化了长序列 attention 的并行划分和访存效率\citep{dao2023flashattention2}；MQA/GQA 通过减少 KV head 数降低 Decode 阶段 KV Cache 规模和内存带宽压力\citep{shazeer2019fast,ainslie2023gqa,pope2022efficiently}；H2O、Scissorhands、KIVI、KVQuant 和 InfiniGen 等工作则分别从 KV eviction、重要 token 保留、KV 量化和动态预取等角度降低 KV Cache 的显存占用或访存流量\citep{zhang2023h2o,liu2023scissorhands,liu2024kivi,hooper2024kvquant,lee2024infinigen}。这些工作说明，Decode 阶段的核心瓶颈正在从"算得快"转向"KV Cache 能否以合适布局、合适精度和合适粒度被快速访问"。

从服务系统层看，DeepSpeed Inference、FlexGen、TurboTransformers、SpecInfer 和 SGLang 分别围绕多 GPU/异构内存推理、单 GPU 高吞吐 offloading、Transformer serving kernel、投机推理和结构化程序执行优化服务能力\citep{aminabadi2022deepspeedinference,sheng2023flexgen,fang2020turbotransformers,miao2023specinfer,zheng2023sglang}。Sarathi 和 Sarathi-Serve 进一步将 prefill 切块与 decode 批处理结合，缓解混合部署中 prefill/decode 相互干扰的问题\citep{agrawal2023sarathi,agrawal2024sarathiserve}。这些系统优化与本课题关注的 PD 分离、KV Cache 负载感知和动态 CP 共同指向同一趋势：长文本推理服务需要在请求级、阶段级和序列级同时做资源调度。

然而，长文本推理对系统提出了更强的要求。长上下文输入会放大 Prefill 阶段的计算开销，使 TTFT 从毫秒级或秒级上升到数秒甚至数十秒；同时，历史 KV Cache 随上下文长度和并发请求数线性增长，Decode 阶段的显存压力和访存开销显著增加。单纯依靠通用 batching 或显存管理技术，难以同时满足长输入低 TTFT、长输出低 TPOT、高吞吐和高并发。因此，近年来研究重点逐渐从单点算子优化转向面向推理阶段、序列维度和集群资源的系统级优化，其中 PD 分离和 CP 并行是最具代表性的两条路线。

\subsection{Prefill-Decode 分离研究现状}

国际上，PD 分离的思想首先由一系列工作系统化提出。Splitwise 最早指出 Prefill 和 Decode 分别呈现计算密集和访存密集特征，可部署在不同类型设备上\citep{patel2023splitwise}。DistServe 将其发展为面向 SLO 的系统架构，将两阶段分配到不同 GPU，分别针对 TTFT 和 TPOT 约束进行资源和并行策略协同优化，并考虑阶段间 KV Cache 传输带宽\citep{zhong2024distserve}。Mooncake 进一步从 KV Cache 视角构建分离式架构，利用 GPU 集群中未充分使用的 CPU、DRAM、SSD 等资源构建分层 KV Cache 存储，将 KV Cache 的生成、传输、缓存和调度纳入系统设计\citep{qin2024mooncake}——该工作表明长文本下 PD 分离的瓶颈会从计算迁移到 KV Cache 生命周期管理。LoongServe 则从弹性序列并行角度处理长短请求和不同阶段间资源需求差异，为 PD 分离之外的动态并行服务提供了重要参考\citep{wu2024loongserve}。开源推理框架方面，vLLM 已集成 disaggregated prefilling，vLLM-Ascend 进一步支持基于 Mooncake 的 PD 分离方案，包括 MooncakeConnector 和 MooncakeLayerwiseConnector\citep{vllmascendpd2026,vllmascenddeepseekpd2026}。国内方面，昇腾 MindIE 将 PD 分离作为关键特性，与 Continuous Batching、Page Attention、FlashDecoding 等机制协同使用；昇腾大规模专家并行方案将 P 和 D 部署在不同服务器上，通过高速互联传输 KV Cache，官方技术文章明确指出了混合部署下资源利用不足和阶段间干扰问题\citep{mindie2026,ascendpd2025,ascendexpert2026}。

总体来看，PD 分离已形成较清晰的技术共识：Prefill 和 Decode 具有不同资源特征，应在系统层面解耦。但现有研究在昇腾平台适配方面存在明显不足。首先，现有工作主要基于 NVIDIA GPU 和 CUDA 生态，其通信原语和缓存布局与昇腾平台差异显著。其次，PD 分离会引入额外 KV Cache 传输成本，而昇腾高计算/访存比会放大 KV 传输和 D 侧访存之间的压力耦合——当 D 侧的 KV Cache 拉取、layout 重排和 PageAttention 访问缺乏针对性优化时，昇腾有限的 HBM 带宽将同时承受三方面压力，P 侧节省的 TTFT 可能被 D 侧 TPOT 抖动完全抵消。特别地，当 PD 分离与 CP 同时使用时，KV Cache 需从 P 侧传输到多个 D 副本，传输链路的正确性与效率直接影响 CP 分片的数据可靠性和端到端延迟。因此，昇腾上的 PD 分离需要将 KV 传输、布局转换、通信拓扑和访存瓶颈作为整体来优化，为上层 CP 提供可靠的数据通路。

\subsection{上下文并行研究现状}

上下文并行的核心思想是沿序列维度切分长上下文，使一个请求的长序列计算分布在多个设备上完成。与数据并行按请求或样本划分、张量并行按隐藏维度或矩阵维度划分、流水并行按层划分不同，CP 直接针对长上下文本身进行切分，因此特别适合解决长 prompt 带来的单设备显存和时延瓶颈。作为对比，张量并行、流水并行、ZeRO 和多维并行已在 Megatron-LM、GPipe、ZeRO、Megatron 等训练系统中被充分研究，主要服务于参数和激活显存扩展\citep{shoeybi2019megatron,huang2019gpipe,rajbhandari2020zero,narayanan2021megatron}；而 MoE 相关的 GShard 和 Switch Transformer 进一步引入专家并行与 all-to-all 通信，对推理阶段的负载均衡和同步等待提出了更高要求\citep{lepikhin2020gshard,fedus2021switch}。

Ring Attention 是上下文并行方向的代表性工作之一。该方法采用 blockwise attention，将序列划分为多个 block，并通过环形通信在设备间传递 KV block，使每个设备可以在计算本地 attention 的同时与其他设备交换 KV 数据\citep{liu2023ringattention}。Ring Attention 的重要特点是保持精确注意力计算，不依赖稀疏化或近似剪枝，并通过通信与计算重叠来提升长序列可扩展性。它为后续长上下文训练和推理中的 ring-style CP 提供了基础思路。

DeepSpeed-Ulysses 则从另一条路径推动了序列并行发展。它通过沿序列维度切分输入，并利用 all-to-all 通信在注意力头维度和序列维度之间重排数据，从而支持极长序列 Transformer 训练\citep{jacobs2023deepspeedulysses}。Ulysses 方案在部分模型结构和网络条件下具有较高效率，但对 attention head 数量与并行度的可整除关系存在约束。后续 USP 等工作尝试统一 Ulysses 和 Ring Attention 两类方案，结合二者在通信模式、模型适配性和拓扑适配性上的优缺点，形成更通用的长序列并行方法\citep{fang2024usp}。昇腾 MindSpeed 的 Hybrid 长序列并行也采用融合 Ulysses 与 Ring Attention 的思路，以缓解单一方案在 GQA/MQA 模型和小序列块场景中的局限。

面向推理场景，Context Parallelism for Scalable Million-Token Inference 将 CP 明确用于长上下文大模型推理，并设计了 pass-KV 和 pass-Q 等精确 ring attention 变体，覆盖 full prefill、persistent KV prefill 和 decode 等用例\citep{zhong2024contextparallelism}。该工作在多节点 H100 集群上展示了长上下文 Prefill 的近线性扩展能力，说明 CP 不仅适用于训练，也可以成为长文本在线推理降低 TTFT 的关键手段。与此同时，Mnemosyne 等工作也围绕百万级上下文推理提出自适应 chunking、Sequence Pipeline Parallelism 和 KV Cache Parallelism 等策略\citep{agrawal2024mnemosyne}，反映出长上下文推理正在从"能否放下"转向"能否高效服务"。

在昇腾生态中，vLLM-Ascend 已经提供 Context Parallel 支持，并将其划分为 PCP 和 DCP 两类。官方文档中，PCP 通过在 Prefill 阶段划分序列维度，让不同设备并行计算不同序列块，以降低长上下文请求的 TTFT；DCP 则在 Decode 阶段沿序列维度分片 KV Cache，减少 TP 域内的 KV 冗余存储，为更大 batch size 和更长上下文提供显存空间\citep{vllmascendcp2026}。vLLM-Ascend 文档还指出，CP 可以与 eager 模式、图模式、prefix cache、chunked prefill、MTP、PD 分离和 MLAPO 等功能协同使用。在官方 Ascend 910C/A3 环境示例中，DeepSeek-R1-W8A8 的 128K 输入在引入 PCP 后 TTFT 从 73.2s 降至 46.0s，Qwen3-235B 的 120K 输入 TTFT 从 33.9s 降至 22.7s，说明 CP 在昇腾长文本推理中已经具备实际优化价值。

CP 的工程实现还需要处理更细粒度的元数据和通信组问题\citep{cpviz2026}。PCP 需要在请求级别维护 query lengths、KV lengths、position ids 等序列属性；DCP 会改变 token 在各 rank 上的归属关系和 slot mapping，需通过 virtual block 管理跨设备 block。CP 优化的核心难点已从算法层面的序列切分延伸到推理框架内部的 block table、slot mapping 和通信组设计。

在此基础上，Dynamic Context Parallelism RFC \citep{vllmdynamiccp2025} 提出 request-level heterogeneous parallelism：短请求走常规 DP-attention 路径（CP=1），长请求由多个 DP-attention 副本协同执行（CP>1），通过 Domain 抽象和跨 DP 调度解决长短请求混部下的负载倾斜问题。该方向表明，CP 的研究重点正在从"能否切分长序列"转向"如何在真实负载中动态分配注意力计算和通信资源"。

不过，CP 在实际系统中也引入了新的复杂性。首先，CP 会改变 KV Cache 的存储与访问方式，需要 block table、slot mapping、cache interleave size 等机制配合；当 CP 与 PD 分离同时使用时，还必须考虑跨 P/D 节点的 KV Cache 传输格式和切分方式。其次，PCP 和 DCP 的收益并不对称：PCP 主要降低长 prompt 的 TTFT，而 DCP 主要节省 Decode 阶段 KV Cache 显存并提高 batch 能力，但也可能带来额外通信和小算子开销。再次，CP 与 TP、EP、DP、MoE、量化、图模式、prefix cache 等功能之间存在组合约束，尤其是在昇腾平台上需要满足具体算子、通信域和部署拓扑要求。

在昇腾平台上，DCP 的收益不仅体现在显存节省，更体现在 Decode 访存压力的削减。由于昇腾高计算/访存比放大了每次 Decode step 中 KV Cache 遍历的 HBM 带宽压力（前述 $L$ 越大、压力越大），将 KV Cache 按序列维度分片后，每个设备仅需访问其负责分片对应的 KV 数据，HBM 读取量随 CP 度近似线性下降。因此，DCP 在昇腾长上下文 Decode 中的作用不仅是"省显存"，更是"降访存"——用可控的跨卡通信换取 HBM 带宽压力的缓解，而这恰恰是对昇腾高计算/访存比短板的对症下药。由此引出一个新问题：如何根据请求的上下文长度和当前负载强度，在 CP=1（DP 路径）与全量 CP（域内全部副本协同）之间在线二选一，使得 KV 访存压力、跨卡通信开销和显存占用三者之间取得平衡？

\subsection{MoE 推理的负载均衡与同步优化}

MoE 模型在推理阶段面临特有的负载均衡挑战。GShard\citep{lepikhin2020gshard} 和 Switch Transformer\citep{fedus2021switch} 在训练中引入专家容量因子（capacity factor）和辅助负载均衡损失，通过限制每个 expert 处理的最大 token 数来避免单一 expert 过载。然而在推理场景中，token 的路由分布由输入内容决定且不可控，容量因子过小会导致 token 丢弃、精度下降，容量因子过大则计算资源利用率低。DeepSpeed-MoE 等工作通过 expert 并行与 all-to-all 通信的流水线重叠来降低通信延迟，但在 Decode 阶段 token 逐个生成，计算与通信的重叠窗口极窄。近年针对 MoE 推理的优化方向包括：expert 放置优化（将高频 expert 副本分布到不同设备以减少 all-to-all 流量）、expert 动态选择（跳过负载过重的 expert 或降级路由）、以及 expert 并行度与 DP 度的联合配置。上述工作在通用 GPU 平台上取得了一定效果，但均未针对昇腾平台的高计算/访存比特征进行适配——在昇腾上，副本间 KV Cache 差异导致的 attention 完成时间差比 GPU 大得多，all-to-all 同步等待被 HBM 带宽短板剧烈放大，仅靠 expert 侧的负载均衡难以消除 MoE bubble。此外，这些工作与 CP 的协同尚属空白——CP 通过 KV 分片从 attention 侧直接压缩副本间时间差，与 expert 侧优化形成互补。

\section{动态上下文并行调度方法}

\subsection{问题分析与总体框架}

\textbf{MoE bubble 的形成。}在 MoE 模型的 Decode 批处理中，每个 DP 副本承载的请求组合不同，各副本累积的 KV Cache 总量存在差异。KV Cache 总量越大的副本，attention 阶段需从 HBM 读取的 KV 数据越多，访存耗时越长。而 MoE 层的 all-to-all 通信要求同一同步组内的所有副本对齐后才能进行专家路由分发——先完成 attention 的副本必须等待最慢的副本。在昇腾平台上，这一等待被剧烈放大：昇腾 910B 的 HBM 带宽仅 1.2 TB/s，算力/带宽比约 267，约为 H100（148）的 1.8 倍。相同 KV Cache 差异在昇腾上产生的 HBM 读取时间差远大于 GPU，最慢副本的 arrival time 被进一步推迟，大批计算单元在 all-to-all 入口空转——形成 MoE bubble（图~\ref{fig:moe-long-request-blocking}）。而且昇腾 HBM 容量相对较小，超长请求的 KV Cache 即使能放入显存，其遍历产生的 HBM 读取时间也已远超 SLO 允许的 ITL 上限，副本间读取时间差异在 all-to-all 入口被进一步放大为严重 bubble。

\textbf{动态 CP 解法。}CP 沿序列维度将 KV Cache 分片到多个副本，使单副本 HBM 读取量降至约 $1/|D_\text{full}|$，同时各副本同步完成 attention 后同时到达 all-to-all——这是消除 MoE bubble 的直接手段。但 CP 有跨卡通信代价。前期基于 DeepSeek-V2-Lite 的实验（图~\ref{fig:dp-dcp-long-context}）表明：低负载（$\leq$4 rps）时全量 DCP 大幅优于 DP（1M 上下文 P90 ITL 10.1 vs 27.7 ms），高负载（16 rps）时反而不及 DP（61.3 vs 53.8 ms）。结论：不能对所有请求统一启用 CP，需要\textbf{运行时触发}——超长请求启用 CP 消除 bubble，常规请求保持单副本避免不必要通信。

\textbf{三层支撑框架。}动态 CP 的落地需要两个前提。第一，PD 分离下 KV Cache 的跨节点传输需要保证正确性——P/D 两侧的 TP/PP 异构可能导致 layout 错位，而对 GQA/MHA 模型这直接导致推理输出错误。这是 PD 分离自身的基础问题。在此基础上，CP 将 KV Cache 分片到多个 D 副本，若传输 layout 错位，分片会把错误扩散到全部参与副本——因此数据通路的正确性也是 CP 的前提。第二，运行时触发需要判断该请求应以单副本执行还是触发全量 CP——这依赖两个信息：常规执行时的目标副本选择，以及该副本当前负载能否满足请求的 SLO。两者共同构成一个能感知各副本 KV Cache 负载的调度基线。因此本课题的方案由三层组件构成：

\begin{enumerate}
    \item \textbf{数据通路 — KV Cache 跨节点高效传输}：保证 P→D 的 KV Cache layout 正确，为 CP 分片提供可靠数据基础
    \item \textbf{决策基线 — 基于 KV usage 的副本负载感知}：以 KV Cache 使用量为指标感知副本负载，为 CP 触发提供判断依据
    \item \textbf{核心机制 — 动态 CP 协同执行}：根据负载感知结果运行时触发全量 CP，通过跨副本协同执行消除 MoE bubble
\end{enumerate}

\subsection{数据通路：KV Cache 跨节点高效传输}

\textbf{问题：PD 分离下 KV 传输的正确性与效率。}PD 分离要求 P 侧将 KV Cache 传输到 D 侧，但昇腾上的这一传输面临双重挑战。首先是正确性问题：P/D 两侧的并行配置往往异构，P 侧倾向高 TP 加速 Prefill，D 侧倾向低 TP 扩大 batch。对 GQA/MHA 模型，KV head 随 TP rank 切分——例如 Qwen3-235B 在 P 侧 TP=16 时每 rank 仅持有 4 个 KV head 中的 1 个分片，D 侧若按默认路径拉取将出现 KV head 缺失或顺序错误，直接导致推理输出错误。这是 PD 分离自身的正确性问题，不依赖 CP 也存在。其次是效率问题：昇腾 D 侧 HBM 带宽仅 1.2 TB/s 且已被 Decode 访存高度占用，传输后的 layout 转换若低效将直接推高 TPOT。此外，当启用动态 CP 时，KV Cache 需分片到多个 D 副本，传输链路的正确性直接影响 CP 分片的数据可靠性——若 layout 错位，分片会将该错误扩散到全部参与副本。

\textbf{设计。}围绕 MooncakeConnector 展开，采用 D-pull 模式（D 侧主动拉取而非 P 侧推送），避免 P-push 在 D 侧额外开辟接收缓冲区和显存拷贝——这对 HBM 带宽紧张的昇腾 D 侧尤为关键。设计包含三个要点：（1）拓扑感知源端选择：Connector 感知 P/D 两侧 TP、PP、layer partition 配置及 HCCL/HCCS 互联拓扑，为每个 D rank 选择延迟最低的 P rank 集合，MLA 场景随机选择以负载均衡，GQA 场景按 TP 切分精确匹配，跨机架优先同 HCCS ring 内拉取；（2）layout 转换：传输后按 block 粒度进行 split/cat/transpose 以匹配目标端 PageAttention 排布；（3）生命周期管理：D 侧完成本地写入后再释放 P 侧缓存。该设计使数据通路既独立解决 PD 分离的传输正确性问题，又为动态 CP 提供可靠的分片数据基础。

\textbf{layout 转换优化。}layout 转换是性能关键路径。torch 原生 \verb|reshape|/\verb|transpose| 逐 block 触发独立 kernel launch（昇腾 NPU 上每次数十微秒，层数深 block 多时累积至百毫秒级），且 split→cat→transpose 三个算子各执行一次 HBM→UB→HBM 往返。第一步已通过昇腾 NPU 自带 \verb|_reshape_and_cache| 替换 torch 算子，延迟从 155.93 ms 降至约 5.56 ms（图~\ref{fig:reshape-benchmark}）。第二步拟设计专用 \verb|transpose_kv_cache_by_block| 融合算子：融合 split/cat/transpose 为单一 kernel（HBM 访存 3R3W→1R1W），利用昇腾 NPU DataCopy 指令在 Unified Buffer 内完成跨 head 重排，Tiling 策略批量处理多个 block 压缩 launch 次数，针对 MHA/GQA/MQA 分别生成模板化代码路径。预期在 5.56 ms 基础上进一步压缩。

\textbf{现状。}当前已完成 GQA TP 异构、PP 层切分和 MTP 额外层场景的 layout 映射与正确性验证，\verb|_reshape_and_cache| 完成初步优化（155.93→5.56 ms）。

\subsection{决策基线：基于 KV usage 的副本负载感知}

\textbf{问题：运行时触发需要目标副本选择与负载判断。}动态 CP 不能对所有请求都启用，需要判断哪些请求在单副本路径下无法满足 SLO。判断依据包含两步：首先为新请求选择常规执行的目标副本，其次评估该副本当前负载是否足以承载新请求。现有调度器按请求数或队列长度做负载均衡，这在昇腾上存在根本性错配：Decode 延迟由 KV Cache 的 HBM 读取时间主导，而非请求数。两个副本请求数相同但 KV Cache 总量差 10 GB，HBM 读取时间可差数倍，KV Cache 重的副本成为访存 straggler——在 MoE 场景下，它会拖慢整个 all-to-all 同步（图~\ref{fig:moe-long-request-blocking}）。因此需要一种反映 HBM 压力的负载指标，指导副本选择。

\textbf{核心洞察：以 KV Cache 使用量替代请求数。}在昇腾平台上，KV Cache 访问量直接决定 Decode step 的 HBM 读取时间，均衡各副本的 KV usage 等价于均衡各副本的 Decode 延迟。本组件基于 vLLM 设计中心化调度框架，核心是 CentralizedScheduler，维护所有 DP 副本的 KV Cache 使用量（以占用 block 数计量），对新 Decode 请求选择当前 KV usage 最小的副本（min(KV usage) 策略）。KV usage 通过 block table 的已分配量即可获取，无需额外遍历 HBM。

\textbf{设计要点。}（1）Domain：一组 DP-attention 副本组织为 DPLB 调度域，CentralizedScheduler 在每个 Domain 内以 min(KV usage) 为主策略分发请求，batch 均衡为辅助约束。（2）KV usage 感知与更新：调度器在请求分配时递增目标副本的估值，请求完成后递减，维持全局视图准确性。（3）请求分发流程：新请求 → 查询各副本 KV usage → 选最小者 → 下发执行。关键路径仅涉及数值查询与比较，延迟在微秒级（图~\ref{fig:centralized-min-kv-usage}）。

\textbf{对 CP 的支撑。}min(KV usage) 选出最轻载副本后，动态 CP 的触发模块判断该副本当前负载能否满足新请求的 SLO——能则走常规单副本路径，不能则触发全量 CP。大多数常规请求由本组件覆盖，只有超长请求触发 CP。

\subsection{核心机制：动态 CP 协同执行}

\textbf{问题：单副本 HBM 带宽的物理极限。}min(KV usage) 覆盖了大多数常规请求，但当一个请求的上下文极长时，即使最轻载副本，其 HBM 带宽仍不足以在 SLO 内遍历完整 KV Cache。昇腾 910B 的 HBM 带宽（1.2 TB/s）仅为 H100（3.35 TB/s）的约 1/3，单副本遍历数 GB 量级 KV Cache 所需时间远高于 GPU，副本间 arrival time 差异由此被剧烈放大，在 all-to-all 入口形成严重 bubble。此时仅靠选择轻载副本无法解决问题——必须突破单副本执行模式。

\textbf{运行时触发：CP 什么时候开。}CP 将 KV Cache 沿序列维度分片至域内全部 DP 副本，使单副本 HBM 读取量降至约 $1/|D_\text{full}|$，各副本同步完成 attention 后同时到达 all-to-all——直接消除 bubble。但跨卡通信有代价。实验数据划定了运行时触发的边界：低负载（$\leq$4 rps）CP 收益远超代价，高负载（16 rps）CP 代价反超收益（图~\ref{fig:dp-dcp-long-context}）。因此在 CentralizedScheduler 中增加运行时触发模块：min(KV usage) 选出目标副本后，若该副本剩余 HBM 带宽和 KV Pool 容量预估能满足 SLO，保持 CP=1；否则触发全量 CP，将请求升级为跨副本协同。图~\ref{fig:decode-dynamic-cp} 给出了整体调度框架。

\textbf{协同执行机制。}运行时触发模块决定某请求需全量 CP 后，系统启动以下机制。

（1）全量 CP Domain：在 DPLB Domain 基础上扩展——Domain 为部署配置确定的全部参与副本集合，KV Cache 沿序列维度分片至全部副本。

（2）CrossDPKVCacheManager 与二维 slot mapping：核心数据结构为二维映射图——横轴为 DP rank 索引，纵轴为序列 token 位置，每个 cell 记录对应 token 的 KV Cache 落在哪个 rank 的哪个物理 slot 上，以 interleave 粒度将逻辑序列交错平铺到全部副本。virtual block 向上层屏蔽分布细节，Attention backend 仅通过 virtual block 索引定位跨 rank 数据。图~\ref{fig:dycp-system-architecture} 展示了 PD 分离场景下的分片落位关系。

（4）二维 AclGraph 执行：同一 batch 可能混合 CP=1 短请求与全量 CP 长请求，拟将每个 Decode step 编译为二维 AclGraph（维度：请求数 $\times$ batch token 总数），单次 graph launch 融合两种路径的计算与通信。

运行时触发的关键技术问题包括：KV 访存节省与跨卡通信代价的在线估计模型、以及触发阈值随上下文长度和负载强度自适应调整的策略。

\textbf{展望。}本课题当前方案聚焦于 D 侧 Decode 阶段的动态 CP。以下两个方向留待后续研究：（1）\textbf{可变 CP 度选择}：当前方案在 DP 与全量 CP 之间二选一，决策空间简洁、机制可控。未来可扩展为可变 CP 度（CP=1、2、4、8 等），仅选取 KV usage 最低的部分副本参与协同，进一步降低中等长度请求的通信代价，需解决动态 CP 度下的跨副本缓存映射调整、通信组重配置及更复杂的在线估计模型等问题。（2）\textbf{Prefill 侧 PCP 运行时触发}：当 prompt 极长时，单卡 Prefill 的 TTFT 可能远超 SLO，需选择性启用 PCP 将序列切分到多个 P rank 并行计算。但与 Decode 侧不同，PCP 的权衡在于计算-通信比而非访存-通信比，且 P 侧启用 PCP 后 KV Cache 分布在多个 P rank 上，数据通路需支持从多源端聚合或按 D 侧 layout 直接分片传输，避免在 P 侧 gather 引入额外延迟。

\subsection{预期目标}

本课题预期形成一套以动态 CP 缓解昇腾长上下文推理 KV Cache 访存瓶颈为核心的推理优化方法，并在真实模型和推理框架中验证。具体目标包括：

\begin{enumerate}
    \item 完成 KV Cache 跨节点传输与布局适配，支持 GQA/MHA/MQA、TP 异构和 PP/MTP 场景；通过 NPU 自带算子与专用融合算子将 layout 转换开销压缩至可忽略水平，为 CP 分片提供正确的数据通路。
    \item 完成基于 KV usage 的中心化负载感知调度，验证 min(KV usage) 策略对感知副本 HBM 压力的有效性，为 CP 触发提供可靠的决策基线。
    \item 完成动态 CP 协同执行机制，包括运行时触发策略、CrossDPKVCacheManager（二维 slot mapping）、Attention 聚合、二维 AclGraph，并通过实验验证不同上下文长度和负载下动态 CP 对消除 MoE bubble 和改善尾延迟的效果。
\end{enumerate}

\section{拟采用的研究方法、技术路线、实验方案}

\subsection{技术路线}

本课题的技术路线按"瓶颈量化 → 数据通路（KV Cache 传输） → 决策基线（负载感知调度） → 核心机制（动态 CP 协同执行）"四个阶段推进，与研究内容一一对应。

\begin{enumerate}
    \item 瓶颈量化阶段：在昇腾环境中部署典型 MoE 长文本模型，在不同上下文长度（4K 至 1M）下测量混合部署、PD 分离、静态 CP 和动态 CP 配置的 TTFT、TPOT、ITL、吞吐和显存占用，重点采集 HBM 读写量、AI Core 利用率、MoE bubble 时间和 KV Cache 传输时间的分阶段分解数据。量化"长上下文 → KV 访存放大 → MoE bubble → 昇腾算力空转"这一核心瓶颈。
    \item 数据通路阶段：围绕 Mooncake Connector，完成 TP 异构、PP/MTP 层切分和 KV Cache 布局转换，利用 NPU 自带算子完成初步优化，设计专用融合算子进一步降低 layout 转换开销，保证 CP 分片的数据正确性。
    \item 决策基线阶段：在传输正确性得到保证的基础上，实现 CentralizedScheduler 和 min(KV usage) 负载感知策略，搭建 Domain 和 KV usage 感知与更新机制，为动态 CP 触发提供决策基线。
    \item 核心机制阶段：在负载感知调度和 KV Cache 传输通路之上，实现动态 CP 协同执行机制——运行时触发策略、CrossDPKVCacheManager（二维 slot mapping）、Attention 聚合、二维 AclGraph。通过长短请求混合场景和不同 prompt 长度负载，评估动态 CP 对消除 MoE bubble 和改善尾延迟的效果。
\end{enumerate}

\subsection{实验方案}

实验模型方面，拟选择昇腾生态中已适配的典型 MoE 长文本模型，如 DeepSeek 系列、Qwen 系列等，覆盖 MLA、GQA 等注意力结构。实验平台方面，拟基于昇腾 910 系列或实验室可用昇腾集群，使用 CANN、torch-npu、vLLM-Ascend 等推理框架完成部署；在条件允许时，选取 NVIDIA GPU 平台作为对照，展示两类硬件在 HBM 访问压力和 MoE bubble 程度上的差异。实验负载方面，前期已完成 4K、128K、256K、512K、1M 上下文长度和 1--16 rps 负载下的 DP 与静态全量 DCP 基线对比（见图~\ref{fig:dp-dcp-long-context}），为动态 CP 提供了静态上界和下界参考。后续将补充三组实验：动态 CP 触发实验（在不同上下文长度和负载下对比静态全量 CP 与动态 CP 的 ITL 分布、MoE bubble 时间和 QPS）、消融实验（分别测试仅数据通路 + 决策基线、数据通路 + 全量 CP 无运行时触发、三层完整方案，量化各组件的独立贡献和叠加收益），以及 P/D 配比和长短请求混合比例实验（在不同 P/D 配比下评估整体优化效果，给出经验性配比建议）。

对比基线包括：未启用 PD 分离的混合部署方案、启用 PD 分离但未针对 TP 异构优化的方案、启用通用 KV Cache 重排序的方案、启用静态 PCP/DCP 的单独优化方案，以及本课题提出的数据通路 + 决策基线 + 动态 CP 三层协同方案。消融实验中增加仅启用部分组件的配置（如仅数据通路 + 全量 CP 无运行时触发）。评价指标包括 TTFT、TPOT、ITL P50/P90/P95/P99、MoE bubble 时间、归一化 QPS、显存峰值、HBM 读写量及带宽利用率、AI Core 利用率、KV Cache 传输时间、layout 转换时间、跨副本负载均衡程度和推理输出一致性等。特别地，通过 MoE bubble 时间随上下文长度和负载的变化曲线，量化动态 CP 对消除昇腾 MoE bubble 的效果。

\section{可行性分析}

本课题具有较好的可行性。首先，PD 分离、CP 并行、PagedAttention、Mooncake Connector 等机制已经在论文系统和开源框架中形成基础实现，为本课题提供了明确的技术起点。其次，昇腾平台已具备 CANN、HCCL、AscendDirectTransport、vLLM-Ascend、MindIE 等软件栈能力，能够支撑多卡推理、KV Cache 传输和长上下文实验。再次，前期材料中已经对 PD 分离场景下的 KV Cache 传输、GQA TP 异构重排序、PP/MTP 层划分和 NPU 自带算子优化进行了初步分析，说明本课题的问题具有真实工程来源，研究路径较为清晰。

同时，本课题也存在一定挑战。KV Cache 布局受模型结构、并行方式和框架实现共同影响，错误的映射关系会直接导致推理精度异常；动态 CP 会引入跨 DP block pool 管理、通信组选择和运行时调度粒度等新问题。针对这些挑战，本课题采用渐进式实现策略：先打通数据通路和决策基线，再在二者之上实现动态 CP 触发与协同执行；先验证各组件的独立效果，再推进三层协同的端到端稳定性验证。

一个需要直面的技术风险是 HCCS/RDMA 带宽能否承载动态 CP 的跨卡通信量。对此，前期 DP 与静态全量 DCP 的对比实验提供了直接的上界参考：静态全量 DCP 对所有请求统一启用 CP 分片——短请求（在线负载中通常占 99\% 以上）也需参与跨卡通信——其总通信量构成动态 CP 的最坏情况上界。本方案仅对超长请求选择性启用 CP，绝大多数短请求保持 CP=1，总通信量严格低于静态全量 DCP。实验数据表明，即使在该上界条件下，低负载（$\leq$4 rps）时全量 DCP 的 P90 ITL 仍低至 10.1 ms，说明 HCCS 带宽本身足以承载 CP 通信；高负载（16 rps）时全量 DCP 因通信代价而劣于 DP，但运行时触发在负载升高后可自动退避为 DP，使实际通信量始终受控。因此 HCCS 带宽不构成阻塞性风险——系统始终有退路：通信量以静态全量 DCP 为上界、以 CP=1 为下界。

\section{已有科研基础与所需的科研条件}

\subsection{已有科研基础}

本课题已有较充分的前期基础。前期调研已经梳理了 Splitwise、DistServe、Mooncake、Ring Attention、DeepSpeed-Ulysses、Context Parallelism for Scalable Million-Token Inference 等代表性工作，明确了 PD 分离和 CP 并行在长文本推理中的作用边界。工程方面，已分析并改造 vLLM-Ascend 中 Mooncake Connector 在 PD 分离场景下的 KV Cache 传输流程，识别了 DeepSeek MLA 模型与 Qwen GQA/MHA/MQA 模型在 TP 域内 KV Cache 一致性方面的差异，并完成 GQA TP 异构、PP/MTP 层划分和 KV Cache 重排序等核心问题的初步设计与实现。

此外，已分析 CP-Viz 项目中的 CP 可视化材料，对 PCP/DCP 与 TP 组合后的 rank layout、slot mapping 和 virtual block 管理建立了直观理解，为本课题设计 PD+CP 下的 KV Cache 传输策略提供了参考。

同时，已在 vLLM 社区提出 Dynamic Context Parallelism RFC \citep{vllmdynamiccp2025}，该 RFC 中 Domain 抽象、跨 DP 调度和 attention 聚合等设计，与本课题关注的 PD 分离和昇腾运行时适配具有直接关联。在此基础上，前期已在 PD 分离 Decode 节点完成 DP 与静态全量 DCP 的对比实验：数据表明低负载下全量 DCP 可大幅降低长上下文尾部延迟（1M、1 rps 时 P90 ITL 从 27.7 ms 降至 10.1 ms），但高负载下全量 DCP 反而不及 DP（1M、16 rps 时全量 DCP 的 P90 ITL 为 61.3 ms 而 DP 为 53.8 ms），这一反转直接验证了动态 CP 的必要性，也为本课题的核心机制提供了明确的优化目标和评价基线。

在具体技术问题上，前期工作已经取得以下阶段性进展：第一，GQA TP 异构场景下，D 节点能够从正确的 P rank 拉取 KV Cache，并在本地 block 内完成重排序；第二，PP 场景下能够根据 P 节点 PP stage 分组拉取不同层的 KV Cache，并写入 D 节点对应地址；第三，MTP 开启后通过显式配置 layer partition 解决默认层划分函数无法感知额外层的问题。上述基础表明，本课题并非从零开始，而是在已有系统实现和验证结果基础上继续完成实验闭环、消融分析和论文整理。

\subsection{所需科研条件}

本课题所需科研条件主要包括硬件平台、软件环境、模型与数据集以及性能分析工具。硬件方面，需要具备多张昇腾 NPU 的服务器或集群环境，并尽可能具备高速互联能力，以支持 PD 分离、CP 并行和跨节点 KV Cache 传输实验。软件方面，需要安装匹配版本的 CANN、驱动固件、torch-npu、vLLM-Ascend、MindIE 或相关推理框架，并具备编译和调试自定义算子的环境。模型方面，需要准备 DeepSeek、Qwen 等具有代表性的长上下文模型及其量化版本，以覆盖 MLA、GQA/MHA/MQA 等注意力结构。工具方面，需要使用日志、profiling、显存监控、通信监控和 benchmark 工具采集 TTFT、TPOT、QPS、显存和算子开销等指标。
